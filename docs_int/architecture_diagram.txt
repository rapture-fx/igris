PHASE 14 INTEGRATION POINTS:
============================

1. TENANT AUTHENTICATION MIDDLEWARE
   Location: internal/middleware/tenant.go (NEW)
   
   Responsibilities:
   - Extract tenant ID from Authorization header or JWT
   - Validate tenant is active/authorized
   - Load tenant config (budget, rate limits, policies)
   - Store TenantContext in request context
   
   Placement in stack:
   recover -> cors -> traceID -> [TENANT_AUTH] -> requestLogger

2. TENANT CONTEXT
   Type: TenantContext struct
   Fields:
   - TenantID string
   - TenantAPIKey string
   - UserID string
   - Roles []string
   - Config *TenantConfig (budget, policies, etc.)
   
   Stored in: c.Locals("tenant_context")

3. BYOK VAULT ENDPOINTS
   Location: internal/api/routes_vault.go (NEW)
   
   Endpoints:
   POST   /v1/tenants/{tenantID}/vault/keys       # Upload BYOK
   GET    /v1/tenants/{tenantID}/vault/keys       # List keys
   PUT    /v1/tenants/{tenantID}/vault/keys/{id}  # Rotate key
   DELETE /v1/tenants/{tenantID}/vault/keys/{id}  # Delete key
   POST   /v1/tenants/{tenantID}/vault/validate   # Validate keys
   
   Handler: VaultHandler (NEW in internal/api/vault_handler.go)
   
   Uses: internal/vault/ package (NEW)
   - vault/encrypt.go - Encryption/decryption
   - vault/validator.go - Key validation
   - vault/storage.go - Persistent storage

4. POLICY ENDPOINTS
   Location: internal/api/routes_policy.go (NEW)
   
   Endpoints:
   GET    /v1/tenants/{tenantID}/policies              # List policies
   POST   /v1/tenants/{tenantID}/policies              # Create policy
   PUT    /v1/tenants/{tenantID}/policies/{id}         # Update policy
   DELETE /v1/tenants/{tenantID}/policies/{id}         # Delete policy
   POST   /v1/tenants/{tenantID}/policies/{id}/validate # Validate
   
   Handler: PolicyHandler (NEW in internal/api/policy_handler.go)
   
   Policy config supports:
   - Budget limits (per month, total)
   - Model restrictions (whitelist/blacklist)
   - Provider preferences
   - Token limits (per request, per month)
   - Rate limits (requests/minute)

5. TENANT MANAGEMENT ENDPOINTS
   Location: internal/api/routes_tenants.go (NEW)
   
   Endpoints:
   GET  /v1/admin/tenants                 # List all tenants (admin)
   POST /v1/admin/tenants                 # Create tenant (admin)
   GET  /v1/admin/tenants/{id}            # Get tenant (admin)
   PUT  /v1/admin/tenants/{id}            # Update tenant (admin)
   GET  /v1/tenants/me                    # Get current tenant

6. TENANT-AWARE INFERENCE
   Update: internal/api/routes_infer.go

DATA FLOW FOR PHASE 14:
=======================

INFERENCE REQUEST WITH TENANT:
------------------------------

1. Client sends: POST /v1/tenants/acme-corp/infer
   Headers: Authorization: Bearer <jwt-token>

2. TenantAuthMiddleware:
   ├─ Extract tenant from URL path: "acme-corp"
   ├─ Extract JWT token from Authorization header
   ├─ Validate JWT (issuer, expiry, tenant match)
   ├─ Load tenant config from database
   └─ Store in c.Locals("tenant_context")

3. InferHandler.HandleInferWithTenant(c, tenantID, config):
   ├─ Extract TenantContext from c.Locals
   ├─ Use tenant's BYOK key (from vault) for provider auth
   ├─ Apply tenant-specific budget limit
   ├─ Check tenant policy (model/provider restrictions)
   ├─ Call safety controller with tenant budget
   ├─ Route to provider with tenant's key
   ├─ Record metrics per-tenant
   └─ Log audit event with tenant_id

4. SafetyController.PreRequestCheck():
   ├─ Check tenant's monthly budget
   ├─ Check tenant's per-request limit
   ├─ Check token limits
   └─ Return allow/deny + reason

5. InferenceRouter.RouteToProvider():
   ├─ Get tenant's BYOK key from vault
   ├─ Use tenant-specific provider config
   ├─ Make API call
   ├─ Return response

6. AuditLogger.LogEvent():
   ├─ Include tenant_id in event
   ├─ Store to database
   └─ Query by tenant_id

7. Metrics collection:
   ├─ Record per-tenant cost
   ├─ Record per-tenant latency
   └─ Track per-tenant requests


BYOK KEY FLOW:
--------------

1. Tenant uploads key: POST /v1/tenants/{id}/vault/keys
   Headers: Authorization: Bearer <jwt-token>
   Body: {
     "provider": "openai",
     "key": "sk-...",
     "name": "Production Key"
   }

2. VaultHandler.UploadKey():
   ├─ Validate JWT token
   ├─ Extract tenant from JWT
   ├─ Validate key format
   ├─ Test key (ValidateOpenAIKey)
   ├─ Encrypt key with tenant-specific key
   ├─ Store to vault database
   └─ Return key_id

3. Later, during inference:
   ├─ VaultManager.GetKey(tenantID, provider)
   ├─ Retrieve encrypted key from database
   ├─ Decrypt with tenant-specific key
   ├─ Pass to provider for API calls
   └─ Keep decrypted key only in memory


DATABASE SCHEMA ADDITIONS:
--------------------------

CREATE TABLE tenants (
    id VARCHAR(255) PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    status VARCHAR(50), -- "active", "suspended", "deleted"
    created_at TIMESTAMP,
    updated_at TIMESTAMP,
    created_by VARCHAR(255),
    ...
);

CREATE TABLE tenant_users (
    id VARCHAR(255) PRIMARY KEY,
    tenant_id VARCHAR(255) REFERENCES tenants(id),
    email VARCHAR(255) NOT NULL,
    roles JSON, -- ["admin", "user", "viewer"]
    created_at TIMESTAMP,
    ...
);

CREATE TABLE tenant_api_keys (
    id VARCHAR(255) PRIMARY KEY,
    tenant_id VARCHAR(255) REFERENCES tenants(id),
    key_hash VARCHAR(255) NOT NULL,
    description VARCHAR(255),
    created_at TIMESTAMP,
    last_used_at TIMESTAMP,
    ...
);

CREATE TABLE tenant_byok_keys (
    id VARCHAR(255) PRIMARY KEY,
    tenant_id VARCHAR(255) REFERENCES tenants(id),
    provider VARCHAR(50), -- "openai", "anthropic"
    key_encrypted TEXT NOT NULL, -- encrypted with tenant's key
    key_hash VARCHAR(255), -- for validation
    status VARCHAR(50), -- "active", "rotating", "revoked"
    created_at TIMESTAMP,
    expires_at TIMESTAMP,
    created_by VARCHAR(255),
    ...
);

CREATE TABLE tenant_policies (
    id VARCHAR(255) PRIMARY KEY,
    tenant_id VARCHAR(255) REFERENCES tenants(id),
    policy_config JSON, -- entire policy object
    version INT,
    status VARCHAR(50), -- "draft", "active", "archived"
    created_at TIMESTAMP,
    updated_at TIMESTAMP,
    ...
);

ERROR CODES FOR PHASE 14:
-------------------------

400: Bad Request
  - Invalid tenant_id format
  - Invalid policy configuration
  - Invalid key format

401: Unauthorized
  - Invalid JWT token
  - Missing authorization header
  - Token expired

403: Forbidden
  - Tenant not found
  - Tenant suspended
  - Insufficient permissions
  - Policy violation

404: Not Found
  - Tenant not found
  - Vault key not found
  - Policy not found

409: Conflict
  - Duplicate key for provider
  - Policy version conflict

429: Too Many Requests
  - Tenant rate limit exceeded
  - Tenant quota exceeded

451: Unavailable For Legal Reasons
  - Vault key missing (can't proceed with inference)

500: Internal Server Error
  - Database error
  - Encryption/decryption failure
  - Provider error

PERFORMANCE CONSIDERATIONS:
===========================

1. Tenant lookup cache (in-memory with TTL)
   - Cache tenant config for 5 minutes
   - Invalidate on policy updates

2. Vault key caching
   - Cache decrypted keys for 1 hour max
   - Never persist decrypted keys to disk
   - Clear on server restart

3. Database queries
   - Index on (tenant_id, created_at)
   - Index on (tenant_id, provider)
   - Connection pooling (min 5, max 20)

4. Encryption overhead
   - Use AES-256-GCM for tenant data
   - Cache key derivation with PBKDF2


SECURITY CONSIDERATIONS:
========================

1. Key Management:
   - Store only encrypted keys in database
   - Derive tenant encryption key from tenant_id + master_key
   - Never log plaintext keys
   - Rotate master key annually

2. RBAC:
   - Validate JWT token signature
   - Check tenant_id in JWT matches URL
   - Implement role-based access control
   - Log all admin actions

3. Audit Trail:
   - Log all key operations
   - Log all policy changes
   - Log all budget breaches
   - Keep audit logs for 90 days

4. API Key Rotation:
   - Implement key versioning
   - Support gradual deprecation
   - Alert tenant before expiry
