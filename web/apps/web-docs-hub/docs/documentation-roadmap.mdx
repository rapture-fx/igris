# Documentation Roadmap

This page tracks the work required to move the Igris docs from strong product documentation to first-class product documentation.

The main gap is no longer basic coverage. The gap is depth, verification, and machine-consumable product truth.

---

## Must Fix

### 1. Raise API contract confidence

The API reference is now structured well enough that customers will trust it. That means the verification bar must rise with it.

Todo:

- mark every published endpoint as `core`, `supported`, or `preview`
- reduce or hide endpoints that are still documented but weakly verified
- add end-to-end smoke coverage for the primary cloud routes
- add end-to-end smoke coverage for the primary local runtime routes
- validate auth behavior, not just route registration

### 2. Make examples executable

Examples should be treated as product artifacts, not decorative snippets.

Todo:

- test JavaScript, Go, and Rust SDK examples in CI where feasible
- validate OpenAI-compatible examples against the documented base URLs
- validate `curl` examples for auth headers and payload shape
- fail docs validation when a first-class route is missing a runnable example

### 3. Tighten public support signals

Support state should be obvious everywhere the customer makes a decision.

Todo:

- surface support state beyond the API reference on workflow and feature pages
- label cloud, local, and hybrid mode more consistently
- add clearer “preview” treatment for partial SDKs and emerging features

---

## Next

### 4. Deepen workflow documentation

The workflow set is better, but the highest-value customer workflows still need more operator detail.

Todo:

- add rollout guidance for provider key rotation
- add a durable-task operations guide for retries, monitoring, and recovery
- add a receipt verification workflow for audit teams
- add a “choose hosted vs local vs hybrid” decision guide

### 5. Deepen context engineering

Context engineering is now documented conceptually, but it can go further into product implementation patterns.

Todo:

- add design patterns for multi-agent shared context
- document memory vs MCP vs durable-task tradeoffs with more concrete examples
- add context anti-patterns that cause cost, drift, or replay issues
- connect context engineering more directly to SDK and workflow docs

### 6. Improve SDK documentation depth

The SDK pages now have better positioning, but advanced integration guidance is still thin.

Todo:

- add language-specific retry guidance
- add cloud/local/hybrid base-URL switching examples in each first-class SDK
- add receipt and audit retrieval examples where the SDK supports them
- add fleet and vault examples where the SDK supports them

---

## Later

### 7. Make the docs machine-consumable

The docs should serve both humans and agents.

Todo:

- add a dedicated docs MCP surface backed by generated artifacts
- expose endpoint metadata, workflow metadata, support state, and SDK support through MCP tools/resources
- keep MCP output tied to generated docs truth instead of raw prose parsing

### 8. Add docs release discipline

Docs-visible contract changes should be tracked like product changes.

Todo:

- add API release notes to the changelog flow
- require docs review for contract changes
- require docs validation in release pipelines

### 9. Improve search and discovery

The current search is functional, but it is still mostly title-and-keyword driven.

Todo:

- improve search ranking for workflows and API guides
- add better synonym coverage for runtime, fleet, receipts, and MCP terms
- add “related guides” consistently across major documentation pages

---

## First-Class Bar

The docs will feel first-class when these are true:

- the public API surface is trustworthy enough to build against without code spelunking
- examples are runnable and maintained
- deployment modes are obvious
- SDK support is explicit
- workflows connect the product story end to end
- agents and internal tools can consume the docs through structured interfaces, not only prose
