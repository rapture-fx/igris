# SDKs

Igris supports two integration paths:

- **OpenAI-compatible clients** for the fastest path to production
- **Native Igris SDKs** when you need routing metadata, receipt helpers, vault operations, or fleet APIs

The recommendation is simple:

- Start with the OpenAI-compatible API if you want the shortest path to a working integration
- Move to a native SDK when you need Igris-specific product features and a stronger typed client

If you do not already know that you need a native SDK, start with the OpenAI-compatible API first. The native first-class SDKs today are JavaScript/TypeScript, Go, and Rust. Python exists in-repo but remains preview. Java, C#, and Ruby should use the OpenAI-compatible API today rather than being treated as native SDK targets.

For production integration guidance, reusable client construction, and environment-variable patterns, continue with [SDK Integration Patterns →](/docs/sdk-integration-patterns).

## Support Policy

Treat the SDK table as a product support statement, not just a package list:

- **First-class** means the language is part of the maintained customer SDK surface
- **Preview** means the package may be useful, but it should be adopted deliberately
- **OpenAI-compatible** means the safest contract today is the HTTP API through an OpenAI-style client

That distinction matters operationally. If your team wants the strongest support commitment, choose JavaScript/TypeScript, Go, or Rust. If your team mainly needs inference and broad portability, stay on the OpenAI-compatible path.

## OpenAI-Compatible Clients

Any OpenAI SDK can call Igris by changing the base URL. For many teams, this is the right default because it keeps the integration portable while still routing through the product.

**Python**

```python
import os
from openai import OpenAI

client = OpenAI(
    base_url="https://overture.igrisinertial.com/v1",
    api_key=os.environ["IGRIS_API_KEY"],
)

response = client.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": "Hello"}],
)

print(response.choices[0].message.content)
```

**JavaScript / TypeScript**

```typescript
import OpenAI from 'openai';

const client = new OpenAI({
  baseURL: 'https://overture.igrisinertial.com/v1',
  apiKey: process.env.IGRIS_API_KEY,
});

const response = await client.chat.completions.create({
  model: 'gpt-4',
  messages: [{ role: 'user', content: 'Hello' }],
});

console.log(response.choices[0].message.content);
```

Use this path for Java, C#, Ruby, Python, or any other language where you already have an OpenAI-compatible client and do not need the native Igris SDK surface yet.

This is also the right path when you want the shortest evaluation cycle. It gives you one contract that can move between the hosted API and a compatible runtime deployment with minimal application change.

## Native SDKs

Choose a native SDK when you want a product-shaped client rather than a protocol-shaped one. That matters when you are working with receipts, vault operations, fleet controls, or richer Igris metadata.

### JavaScript / TypeScript

```typescript
import { IgrisClient } from '@igris-inertial/sdk';

const client = new IgrisClient({
  baseUrl: 'https://overture.igrisinertial.com',
  apiKey: process.env.IGRIS_API_KEY,
});

const response = await client.infer({
  model: 'gpt-4',
  messages: [{ role: 'user', content: 'Hello' }],
});

console.log(response.choices[0].message.content);
```

For durable streamed inference, the JavaScript SDK can surface both token chunks and the terminal durable-task result from one SSE session:

```typescript
for await (const event of client.streamInference({
  model: 'gpt-4.1-mini',
  messages: [{ role: 'user', content: 'Summarize the deployment risk.' }],
})) {
  if (event.type === 'chunk') {
    process.stdout.write(
      String(
        ((event.data.choices as Array<{ delta?: { content?: string } }> | undefined)?.[0]?.delta?.content) ?? ''
      )
    );
  }

  if (event.type === 'task_result') {
    console.log('\nTask ID:', event.data.task_id);
    console.log('Status:', event.data.status);
    console.log('Requested mode:', event.data.requested_mode);
    console.log('Resolved strategy:', event.data.resolved_strategy);
  }
}
```

### Go

```go
package main

import (
    "context"
    "fmt"
    "log"
    "os"

    igris "github.com/igris-inertial/go-sdk"
)

func main() {
    client := igris.NewClient(
        "https://overture.igrisinertial.com",
        os.Getenv("IGRIS_API_KEY"),
    )

    resp, err := client.Infer(context.Background(), &igris.InferRequest{
        Model: "gpt-4",
        Messages: []igris.Message{
            {Role: "user", Content: "Hello"},
        },
    })
    if err != nil {
        log.Fatal(err)
    }

    fmt.Println(resp.Choices[0].Message.Content)
}
```

### Rust

```rust
use igris_inertial::{IgrisClient, InferRequest, Message};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let client = IgrisClient::builder("https://overture.igrisinertial.com")
        .api_key(std::env::var("IGRIS_API_KEY")?)
        .build()?;

    let response = client
        .infer(&InferRequest {
            model: "gpt-4".to_string(),
            messages: vec![Message {
                role: "user".to_string(),
                content: "Hello".to_string(),
                content_parts: None,
            }],
            ..Default::default()
        })
        .await?;

    println!("{}", response.choices[0].message.content);
    Ok(())
}
```

### Python Preview

The Python SDK is present in the repository and can be used experimentally:

```python
from igris import IgrisClient

client = IgrisClient(
    base_url="https://overture.igrisinertial.com",
    api_key="YOUR_IGRIS_API_KEY",
)
```

Treat the Python package as preview until it is explicitly promoted to first-class support. For production Python integrations today, the OpenAI-compatible API remains the safer default unless you are deliberately evaluating the preview package.

## Deployment Mode Guidance

The same integration can point at different Igris deployments without becoming a different product:

- hosted API: `https://overture.igrisinertial.com`
- local runtime: `http://localhost:8080`
- hybrid: keep your application on the hosted API and let Igris coordinate work across runtimes

Use the hosted API unless the workload truly needs on-device execution, offline behavior, or fleet-local control. The more you can keep application code pointed at one base URL strategy, the easier it is to keep the integration clean.

## Request Contract

The core infer request fields are shared across native SDKs:

| Field | Type | Description |
|---|---|---|
| `model` | string | Upstream model name or local runtime model |
| `messages` | array | Conversation messages with `role` and `content` |
| `provider` | string | Optional provider pin |
| `optimize_for` | string | Optional routing hint such as `"latency"` or `"cost"` |

## Code Quality Expectations

Well-written Igris integrations usually share a few traits:

- one constructor owns base URL and auth setup
- credentials come from a secret manager or environment, not source control
- `429`, auth failures, validation failures, and `5xx` responses are handled differently
- cloud, local, and hybrid mode selection happens at startup, not inside business logic
- receipt, audit, and fleet features are adopted intentionally rather than appearing ad hoc in request handlers

When you need the most portable path across languages, default to the OpenAI-compatible client surface. When you need the strongest supported native contract, choose JavaScript/TypeScript, Go, or Rust.
