# Fleet Rollout Workflow

Use this workflow when you need to manage many runtimes as one operational fleet.

This is the customer workflow for:

- seeing registered runtimes
- pushing configuration
- coordinating updates

---

## 1. Confirm runtimes are eligible to participate

Before rollout, make sure each runtime can:

- start cleanly
- reach the hosted product
- register successfully
- report health consistently

If registration is not healthy, rollout is the wrong next step. Fix runtime readiness first, then come back to rollout.

## 2. Inspect current fleet state

Use the fleet inventory surface before making changes. That gives you the real target set, not the target set you assume exists.

## 3. Push configuration deliberately

Use config push for settings changes such as runtime behavior, local model paths, or fallback configuration. Roll configuration changes separately from binary upgrades whenever possible so failures are easier to isolate and rollback decisions are easier to make.

## 4. Roll runtime updates in stages

Use OTA update controls in stages:

1. canary a small set of runtimes
2. watch health and task behavior
3. expand the rollout only after the first slice is stable

Avoid all-at-once rollout unless the fleet is extremely small and the blast radius is acceptable.

## 5. Verify post-rollout health

After configuration or update rollout, confirm:

- runtimes remain visible
- heartbeats continue
- local task execution still succeeds
- customer-facing traffic is unaffected

## Common Mistakes

- Rolling out configuration and binary updates at the same time without a reason
- Skipping canary stages
- Treating runtime download and update operations like ordinary application traffic
