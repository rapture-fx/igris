# Agents

Igris supports four agent patterns: reflection, planning, tool use, and swarms. All run inside the execution envelope with full governance applied.

---

## Reflection Agents

A reflection agent generates an initial response, evaluates its own quality, and regenerates if the quality score falls below a threshold.

**Execution loop:**
1. Generate initial response
2. Score response on a 0.0–1.0 quality scale
3. If score ≥ threshold: return response
4. If score < threshold: regenerate with critique feedback
5. Repeat until threshold met or `max_steps` reached

**Configuration:**
```json
{
  "mode": "reflection",
  "reflection_threshold": 0.8,
  "max_reflection_steps": 3
}
```

**When to use:** Tasks where response quality must meet a minimum bar before the result is returned — code generation, structured output, reasoning tasks.

[Execution Model →](/docs/execution-model)

## Planning Agents

A planning agent breaks down complex tasks into steps, executes each step, observes the result, and adjusts the plan before proceeding.

**Execution loop:**
```
Plan → Act → Observe → Reflect → Plan (repeat)
```

The agent maintains a working plan that is revised after each step. Planning steps consume `max_steps` from the execution envelope.

**Configuration:**
```json
{
  "mode": "planning",
  "max_steps": 10
}
```

**When to use:** Multi-step tasks where the approach depends on intermediate results — research, code generation with testing, multi-stage workflows.

[Execution Model →](/docs/execution-model)

## Tool-Use Agents

A tool-use agent can call external tools as part of inference: HTTP APIs, shell commands, and filesystem operations. Tool calls are governed by the execution envelope's capability grants.

Available tools (each requires an explicit capability grant):

| Tool | Capability | What it does |
|---|---|---|
| HTTP | `tool_http` | GET/POST to external APIs |
| Shell | `tool_shell` | Execute shell commands (sandboxed) |
| Filesystem | `tool_filesystem` | Read, write, list files |

Tool calls are recorded in the execution receipt including the call parameters, response, and latency.

**Configuration:**
```json
{
  "mode": "tools",
  "capabilities": {
    "tool_http": true,
    "tool_shell": false,
    "tool_filesystem": true
  }
}
```

[Tools →](/docs/tools) · [Capability Model →](/docs/capability-model)

## Multi-Agent Swarms

A swarm executes a task using multiple specialized agents in parallel. Each agent contributes a perspective; a synthesizer agent combines the contributions into a final result.

**Execution:**
1. Task is distributed to N specialized agents (researcher, engineer, critic, synthesizer)
2. Agents execute independently
3. Synthesizer receives all outputs and produces the final response
4. Consensus voting is applied for high-stakes decisions

**Configuration:**
```json
{
  "mode": "swarm",
  "swarm_size": 3
}
```

Each agent in the swarm runs its own execution envelope. The swarm's total resource consumption is the sum of all agent envelopes.

## MCP Swarm Mode

MCP Swarm Mode enables peer-to-peer context sharing across multiple engine instances. Instances auto-discover each other via mDNS and share execution context in encrypted storage.

Any instance in the swarm can continue an execution that another instance started. Context is encrypted at rest with AES-256-GCM.

**Use cases:**
- High-availability deployments where any node can handle any request
- Edge deployments where context must persist across reboots
- Multi-robot coordination where agents share mission state

[Memory →](/docs/memory)

## Agent Lifecycle

All agents — regardless of type — follow the same lifecycle:

```
Created → Active → Completing → Completed
               │
               │ (violation or deadline)
               │
          Terminated
```

Lifecycle events are recorded in the execution envelope and queryable via the observability API.

[Agent Lifecycle →](/docs/agent-lifecycle)
