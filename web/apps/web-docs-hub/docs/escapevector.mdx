# EscapeVector

EscapeVector is Igris's intelligent routing engine. It implements Thompson Sampling, circuit-breaker logic, and provider health monitoring to make optimal routing decisions for every inference request.

---

## What It Is

EscapeVector is the core routing decision engine that powers Igris's multi-provider inference coordination. It evaluates available providers, their current health and performance characteristics, and selects the optimal provider for each request.

```
Request → EscapeVector Engine → Provider Selection → Inference
```

EscapeVector runs:
- **In the cloud** — as part of the coordination layer, routing requests across your provider pool
- **On edge devices** — embedded in the Runtime binary, making local routing decisions when multiple models or providers are available

---

## How It Works

EscapeVector continuously tracks performance metrics for each configured provider:

| Metric | Description |
|---|---|
| **Latency** | p50 and p95 response times with exponential decay weighting |
| **Success rate** | Fraction of requests returning valid responses |
| **Cost** | Per-token cost based on provider pricing |
| **Availability** | Current health status from continuous monitoring |

On each request, EscapeVector evaluates these metrics against your routing strategy to select the best provider.

---

## Routing Strategies

### Thompson Sampling (Default)

Thompson Sampling is a Bayesian multi-armed bandit algorithm that naturally balances exploration (trying providers to keep statistics fresh) with exploitation (using the best-known provider).

**How it works:**
1. Each provider has a probability distribution modeling its expected performance
2. On each request, EscapeVector samples from each provider's distribution
3. The provider with the best sampled value is selected
4. After the request completes, the provider's distribution is updated with the observed result

This means routing adapts in real time — a provider that degrades will see its traffic share drop automatically.

### Cost-Optimized

Routes requests to minimize cost per token while maintaining acceptable quality. Useful for high-volume, cost-sensitive workloads.

### Latency-Optimized

Routes requests to minimize response time. Useful for interactive applications where speed is the primary concern.

### Strategy Configuration

```json
{
  "routing": {
    "strategy": "thompson-sampling",
    "fallback_chain": ["anthropic", "openai", "local"],
    "exploration_bonus": 0.1
  }
}
```

## Circuit Breaker

The circuit breaker protects against cascading failures when a provider degrades:

```
                    ┌──────────┐
     Success ──────►│  CLOSED  │────── Requests flow normally
                    └────┬─────┘
                         │ consecutive failures >= threshold
                    ┌────▼─────┐
                    │   OPEN   │────── Requests diverted to next provider
                    └────┬─────┘
                         │ recovery timeout elapsed
                    ┌────▼─────┐
     Success ──────►│ HALF-OPEN│────── Test request to verify recovery
                    └──────────┘
```

**Circuit breaker states:**

| State | Behavior |
|---|---|
| **Closed** | Provider is healthy. Requests flow normally. |
| **Open** | Provider has exceeded the failure threshold. Requests are diverted to the next provider in the fallback chain. |
| **Half-Open** | Testing whether the provider has recovered. A single test request is sent; success closes the circuit, failure reopens it. |

**Configuration:**
```json
{
  "circuit_breaker": {
    "failure_threshold": 5,
    "success_threshold": 3,
    "timeout_seconds": 30,
    "half_open_max_requests": 1
  }
}
```
