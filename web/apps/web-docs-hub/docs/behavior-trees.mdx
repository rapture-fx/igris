# Behavior Trees

Igris currently exposes **two** behavior-tree schemas. Treat them as different layers of the product:

- The **definition schema** used by the cloud control plane and console editor
- The **runtime execution schema** used by the runtime API and native SDKs

If you mix them up, validation will fail.

---

## 1. Cloud Definition Schema

The coordination layer stores graph-style definitions using `nodes` and `edges`.

```json
{
  "name": "shutdown-guard",
  "description": "Temperature-triggered shutdown sequence",
  "nodes": [
    { "id": "n1", "type": "Sequence", "label": "Root", "x": 300, "y": 50 },
    { "id": "n2", "type": "Condition", "label": "Check Temp", "x": 150, "y": 150 },
    { "id": "n3", "type": "Action", "label": "Shutdown", "x": 450, "y": 150 }
  ],
  "edges": [
    { "id": "e1", "source": "n1", "target": "n2" },
    { "id": "e2", "source": "n1", "target": "n3" }
  ]
}
```

This is the schema used by:

- `GET /v1/bt/templates`
- `GET /v1/bt/definitions`
- `GET /v1/bt/definitions/:id`
- `POST /v1/bt/definitions`
- `DELETE /v1/bt/definitions/:id`

---

## 2. Runtime Execution Schema

The runtime and native SDKs use a nested tree representation with lowercase node types.

```json
{
  "type": "sequence",
  "name": "shutdown-guard",
  "children": [
    {
      "type": "condition",
      "name": "check_temp",
      "key": "sensor.temperature",
      "expected": "80"
    },
    {
      "type": "action",
      "name": "shutdown",
      "tool": "http_post",
      "args": {
        "url": "http://localhost:9000/shutdown"
      }
    }
  ]
}
```

This is the schema accepted by the local runtime endpoints:

- `POST /v1/btree/validate`
- `POST /v1/btree/run`
- `POST /v1/btree/deploy`

## Using the JavaScript SDK

```typescript
import {
  Runtime,
  BehaviorTree,
  SequenceNode,
  ConditionNode,
  ActionNode,
} from '@igris-inertial/sdk';

const runtime = new Runtime({ localUrl: 'http://localhost:8080' });

const tree = BehaviorTree.fromJson(
  new SequenceNode('shutdown-guard', [
    new ConditionNode('check_temp', 'sensor.temperature', '80'),
    new ActionNode('shutdown', 'http_post', { url: 'http://localhost:9000/shutdown' }),
  ]).toJSON(),
  runtime,
);

const result = await tree.validate();
console.log(result.valid);
```

---

## Using the Go SDK

```go
package main

import (
    "context"
    "log"

    igris "github.com/igris-inertial/go-sdk"
)

func main() {
    runtime := igris.NewRuntime("http://localhost:8080")
    treeDef := igris.NewSequenceNode("shutdown-guard",
        igris.NewConditionNode("check_temp", "sensor.temperature", "80"),
        igris.NewActionNode("shutdown", "http_post", map[string]interface{}{
            "url": "http://localhost:9000/shutdown",
        }),
    )

    tree := igris.NewBehaviorTree(treeDef, runtime)

    if _, err := tree.Validate(context.Background()); err != nil {
        log.Fatal(err)
    }
}
```

---

## Practical Rule

Use `nodes` / `edges` only when you are talking to the cloud definition API. Use lowercase nested nodes when you are talking to the runtime or a native SDK.

## Durable Execution

By default, behavior tree execution is stateless — a runtime crash loses all tick progress. Attaching a WAL session makes execution crash-recoverable.

When a WAL session is active:
- Each tick writes an `Intent` entry to the WAL before the tree ticks, and a `Committed` entry after
- The blackboard is checkpointed to the coordination layer every N ticks (configurable, default 10)
- Any interruption — deadline, cancellation, or tick error — attaches the last checkpoint to the result so recovery can begin immediately

On failover to a new runtime, the coordination layer forwards the last `ResumeToken` and `blackboard_state`. The new runtime restores the blackboard and resumes ticking from the last committed step. The checkpoint digest is verified before any steps are skipped — a digest mismatch is a hard error, not a silent re-execution from scratch.

```typescript
// JavaScript SDK — attach a WAL session before running
const result = await runtime.runBehaviorTree(treeDefinition, {
  walSession: {
    taskId: '018f4a2b-...',
    checkpointEvery: 10,
  },
});

// result.checkpoint is populated on interruption or completion
// — forward it to the coordination layer for persistence
if (result.checkpoint) {
  await coordinator.saveCheckpoint(result.checkpoint);
}
```

A WAL session requires the runtime to be configured with an Ed25519 signing key. Runtimes without a signing key reject WAL-backed task submissions.
