# Execution Flow

This page traces the path of a request through the Igris Inertial platform from SDK call to signed receipt.

---

## Request Lifecycle

```
1. Application sends request
        │
        ▼
2. SDK serializes to OpenAI format
        │
        ▼
3. Overture receives request
   ├── Authenticates tenant
   ├── Checks budget limit
   ├── Applies routing policy
   └── Selects provider (Thompson Sampling)
        │
        ├──── Cloud provider selected ──────────────────┐
        │                                               │
        ├──── Runtime selected (hybrid mode) ──────┐   │
        │                                          │   │
        ▼                                          ▼   ▼
4. Runtime (if used)                       Cloud provider
   ├── Opens execution envelope            (OpenAI / Anthropic
   ├── Checks capability gates              / Google / etc.)
   ├── Runs inference (local or cloud)          │
   ├── Closes envelope                          │
   └── Signs receipt                            │
        │                                       │
        └───────────────────────────────────────┘
                            │
                            ▼
5. Overture receives response
   ├── Records cost and latency
   ├── Updates provider statistics
   └── Returns response to application
        │
        ▼
6. Application receives response
   └── metadata includes: provider, cost, latency, routing_decision
```

## Step by Step

### 1. SDK Call

Your application uses any OpenAI-compatible SDK pointed at Overture's endpoint.

```python
from openai import OpenAI

client = OpenAI(
    base_url="https://overture.igrisinertial.com/v1",
    api_key="your-igris-api-key"
)

response = client.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": "Explain quantum entanglement"}]
)
```

The request is standard OpenAI format. No Igris-specific fields are required for basic usage.

---

### 2. Overture Routes the Request

Overture receives the request and applies routing logic before forwarding:

**Authentication.** The API key is validated and associated with a tenant. All downstream cost, quota, and policy enforcement uses this tenant context.

**Budget check.** If the tenant has a monthly budget configured and the current spend has reached the hard limit, Overture returns HTTP 402 before forwarding the request.

**Provider selection.** Overture selects a provider from the tenant's configured provider pool. The selection uses current performance statistics, the tenant's routing policy, and real-time provider health.

**Forwarding.** The request is forwarded to the selected provider in the provider's native format. If the provider fails, Overture selects the next provider and retries.

---

### 3. Execution (Cloud or Local)

**Cloud path:** The provider runs inference and returns a response. Overture records latency, token count, and error status.

**Runtime path (hybrid mode):** If Overture's routing selects Runtime as the provider, the request goes to a registered Runtime instance. Runtime opens an execution envelope, enforces capability gates, runs inference (local or cloud), signs the completed envelope, and returns the response.

---

### 4. Response Returns to Application

The response follows OpenAI's response format with additional metadata:

```json
{
  "id": "chatcmpl-abc123",
  "object": "chat.completion",
  "choices": [...],
  "usage": {
    "prompt_tokens": 12,
    "completion_tokens": 87,
    "total_tokens": 99
  },
  "metadata": {
    "provider": "anthropic",
    "model_used": "claude-3-haiku",
    "routing_decision": "thompson-sampling",
    "cost_usd": 0.00021,
    "latency_ms": 312,
    "fallback": false
  }
}
```

## Offline Path

When all cloud providers are unreachable and Runtime is configured as a local fallback:

```
Application → Overture (cloud providers unreachable)
                  │
                  └──► Runtime (local inference)
                            │
                            ├── Phi-3 / Mistral / Llama
                            ├── Signs execution receipt
                            └── Returns response
```

From the application's perspective, the response is identical. The `metadata.provider` field reflects which backend was used.

## Execution Receipts

When Runtime processes a request, it produces a signed execution receipt. The receipt contains:

- Canonical record of inputs and outputs
- Resource usage (tokens, time, tool calls)
- Applied capability gates
- Cryptographic signature

Receipts are stored in Runtime's local database and can be exported for audit. They cannot be altered after signing.
