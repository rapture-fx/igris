# Durable Task Execution

Durable tasks are for long-running AI work that should not be treated like a single short request.

Use them when the workload needs:

- multiple steps
- explicit state progression
- bounded execution over time
- records that remain inspectable after the task completes or fails

This page explains the durable-task model in practical terms and keeps recovery claims aligned with current proof status.

---

## What Durable Tasks Add

Compared with a short synchronous request, a durable task adds:

- task identity
- execution-state tracking across steps
- checkpoint and WAL-oriented structures
- follow-up inspection through task status and receipt-oriented workflows

That makes durable tasks the right fit for longer-running governed work.

## How To Think About The Lifecycle

The durable-task lifecycle is still Request -> Execute -> Verify:

- **Request** submits the task definition
- **Execute** runs the task step by step under boundaries
- **Verify** inspects task status, execution outcome, and receipt-oriented records

## Submitting A Task

```bash
POST /v1/tasks/submit
Authorization: Bearer YOUR_API_KEY
Content-Type: application/json
```

The product supports different submission shapes, but they all become one durable execution workflow underneath.

### Example

```json
{
  "task_type": "agent_workflow",
  "task_definition": {
    "steps": [
      {
        "step_index": 0,
        "model": "gpt-4.1-mini",
        "messages": [
          { "role": "user", "content": "Summarize the Q3 report" }
        ]
      },
      {
        "step_index": 1,
        "model": "gpt-4.1-mini",
        "messages": [
          { "role": "user", "content": "Extract action items from the summary" }
        ]
      }
    ]
  },
  "idempotency_key": "report-q3-2026-run-1"
}
```

## Tracking Task Status

```bash
GET /v1/tasks/TASK_ID
Authorization: Bearer YOUR_API_KEY
```

Typical statuses include:

| Status | Meaning |
|---|---|
| `pending` | Awaiting runtime assignment |
| `dispatched` | Assigned and executing |
| `checkpointed` | Mid-execution with checkpoint state recorded |
| `completed` | All steps finished successfully |
| `failed` | Execution ended with a non-recoverable error |
| `recovering` | Recovery handling is in progress |

Use these states to understand where the work is, not as proof that every recovery path has been demonstrated end to end.

## Checkpoints And Recovery Language

Checkpoint, WAL, and recovery structures are part of the durable-task model, but proof language matters:

- checkpoint and resume structures are present
- durable-task state tracking is real
- full end-to-end kill, restart, and resume behavior should be treated according to [Proof Status](/docs/proof-status) unless you have a reproducible proof artifact

Do not present automatic resume or production-grade recovery as universally proven without that evidence.

## Durable Streaming

Durable-task ideas also appear in some streamed workflows, where a task result and execution artifacts can be surfaced at the end of a stream.

That is useful when you want live output and still need a durable task result to inspect later.

## Common Mistakes

- Treating long-running work like a plain synchronous inference request
- Assuming checkpoint structures automatically mean proven end-to-end recovery
- Promoting recovery semantics more strongly than the available proof artifacts support
- Skipping task-status inspection and going straight to assumptions about the run outcome
