# Igris

Igris helps engineers run AI tasks with governed, verifiable execution.

Direct provider calls are still the right tool for simple chat or one-off prompting. Igris becomes useful when AI output starts doing work: calling tools, crossing system boundaries, touching customer data, or triggering decisions that need to be reviewed later.

The simplest mental model is:

1. **Request** through one Igris API surface.
2. **Execute** with governance, routing, events, and failure handling.
3. **Verify** with signed records and verification-ready receipts.

---

## Request -> Execute -> Verify

### Request

Send a request once. The surface can be a registered action run, a durable task submission, or an MCP tool call — different doors into the same system. The point is not "many products." The point is one execution system that can accept work in a stable, inspectable way.

### Execute

Igris decides how the run should proceed for the deployment you have configured. That can include routing to a runtime, applying capability and policy boundaries, capturing execution events, and surfacing failure paths instead of hiding them behind a plain model response.

### Verify

Igris returns more than output text. The system can also return execution metadata, signed execution records, and receipt material that can be checked after the run. That is the difference between "the model answered" and "the execution can be inspected."

---

## What To Expect From The Current Product

**Governed execution.** Igris is built for runs that need boundaries, not just completions. Capability checks, policy controls, and execution-state visibility are part of the product story.

**Execution visibility.** The system tracks route decisions, execution metadata, and receipt-oriented records so engineers can inspect what happened after a run.

**Verification-ready records.** Signed envelopes and receipts are part of the product today, and the local unified proof demonstrates signature and hash verification on the proof-backed path.

**Honest proof status.** The strongest proven path today is the local unified proof with a mock upstream. Real-provider mode is wired, but it requires sanctioned credentials and was not proven in the prior environment. Advanced areas such as local GGUF fallback, checkpoint recovery, fleet failover, robotics, and multimodal should be treated according to their page-level proof labels.
