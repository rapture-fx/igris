# Circuit Breaker

The circuit breaker is an advanced failure-aware execution mechanism.

Its purpose is to reduce traffic to an upstream path that is repeatedly failing, then probe cautiously to see whether that path has recovered. This helps make failure paths more visible and controlled during execution.

---

## Core States

The common state model is:

- **closed** when the path is healthy enough for ordinary traffic
- **open** when the path should stop receiving ordinary traffic
- **half-open** when the system is probing recovery carefully

This is a classic control mechanism, but in Igris it matters because it shapes which execution paths remain eligible during failure conditions.

## Why It Matters

Without a breaker, the system may keep sending work into a failing path longer than it should.

With a breaker, operators get:

- clearer failure handling
- reduced repeated attempts against a path that is already misbehaving
- a more deliberate recovery probe before normal traffic resumes

## What It Does Not Mean

The breaker is not a blanket guarantee that every execution survives every upstream issue. It is one mechanism in the larger Execute-stage control stack.

Other layers still matter:

- policy
- health
- trust
- explicit deployment choices

## How To Operate It

Use breaker settings to match your tolerance for:

- repeated upstream failures
- recovery probe frequency
- flapping behavior

If a path is bouncing rapidly between states, that is an operational signal worth inspecting rather than something to hide behind automation language.

## Monitoring

Use console and API health views to inspect breaker state and recent failure behavior. Treat those views as execution diagnostics, not as proof that all survival scenarios are fully covered.
