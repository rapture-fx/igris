# Safety & Containment

Igris enforces safety limits at the execution engine level — not at the application layer, where they could be bypassed.

---

## Containment Model

Every execution runs in a containment context. The containment context applies resource limits before the model is invoked and enforces them throughout execution.

### Resource limits

Limits are applied per-execution:

| Limit | Default | Description |
|---|---|---|
| `max_tokens` | 4096 | Maximum output tokens |
| `max_duration_ms` | 30000 | Maximum wall time (30s) |
| `max_steps` | 10 | Maximum tool/planning steps |
| `max_tool_calls` | 5 | Maximum tool invocations per execution |

Limits can be tightened per-tenant or per-request. They cannot be relaxed beyond the configured policy maximum.

### cgroup bounds (Linux)

On Linux deployments, the engine applies cgroup constraints to the execution process:

- **CPU quota**: limits CPU burst during local model inference
- **Memory limit**: prevents unbounded memory growth in local inference
- **I/O limits**: optional disk I/O rate limits for file-system tool use

cgroup enforcement is independent of application code. An agent that attempts to consume more resources than its cgroup allows is throttled or killed by the kernel.

---

## Capability Enforcement

Capabilities are enforced by the engine, not by the model. Even if the model generates output that attempts a disallowed tool call, the engine intercepts and rejects it before the call executes.

The enforcement sequence:

1. Request arrives with a capability grant (or secure defaults are applied)
2. Engine validates the grant against the tenant's policy ceiling
3. Engine begins execution with the validated grant in scope
4. If the model attempts a tool call, the engine checks the grant before executing
5. If the call is outside the grant, the engine records a capability violation and rejects the call
6. Execution continues or terminates depending on the violation policy

Violation events are recorded in the execution receipt. They cannot be suppressed.

---

## Secure Defaults

The engine applies secure defaults when capability grants are not explicitly specified:

| Setting | Default |
|---|---|
| `allow_http` | disabled |
| `allow_shell` | disabled |
| `allow_filesystem` | disabled |
| `max_tokens` | 2048 |
| `max_steps` | 5 |

Tools must be explicitly enabled. The defaults assume no tool use is intended.

---

## Violation Handling

When a capability violation occurs:

1. The violation is recorded in the execution envelope
2. The violating operation is rejected (not executed)
3. The execution either continues (if configured) or is terminated
4. The signed receipt includes the full violation record

Violations are not surfaced as application errors by default. Your application receives a response. The violation is visible in the receipt and in the observability API.

---

## Human-in-the-Loop

For high-stakes decisions, executions can be configured to pause for external approval before completing. The engine holds the execution open, sends an approval request to the configured webhook, and waits for a response before proceeding.

Approval gate events are recorded in the execution envelope: what was held, what approval was received, and when it was granted.
