# Receipts and Audit Workflow

Use this workflow when a run needs to be inspected, verified, and retained after execution.

The practical sequence is:

1. run through a documented Igris surface
2. inspect the execution outcome
3. retrieve the receipt-oriented record
4. verify what can actually be checked
5. retain or export the result for downstream use

---

## 1. Run Through A Documented Igris Surface

Receipts are most useful when the request goes through a documented Igris path. Keep integrations on supported surfaces so execution metadata, receipts, and export workflows line up with the actual run.

## 2. Inspect The Execution Outcome

Start with the immediate execution result:

- response content
- execution metadata
- route decision or provider label where applicable

This tells you what happened during the run. It is useful for debugging and operational review, but it is not the same thing as the receipt itself.

## 3. Retrieve The Receipt-Oriented Record

Use receipt listing and detail endpoints when you need the signed or hash-linked execution record.

- [Execution Receipts →](/docs/execution-receipts)
- [API Reference →](/docs/api-reference)

Treat the receipt surface as the audit artifact. Treat execution history as supporting context, not as a substitute for the receipt.

## 4. Verify With The Right Expectation

Use the strongest verification surface that matches your need.

For the narrow proof-backed path today:

- the local verified run proves signature checks, receipt-hash checks, and receipt-log chain checks
- see [First Verified Run](/docs/first-verified-run)

For the hosted proof route:

- `POST /proof/receipts/verify` compares submitted receipt values against the stored record and returns proof-status information
- it should be described as stored-value comparison and proof-status sync, not as a full public cryptographic verifier

See [Verification](/docs/verification) for the distinction.

## 5. Retain Or Export The Record

Use `GET /v1/receipts/export` when another system, reviewer, or audit process needs the record outside the immediate execution flow.

Choose:

- NDJSON for machine pipelines
- CSV for spreadsheet-oriented workflows

Decide on retention and downstream custody before exporting receipts into another system.

## Common Mistakes

- Treating execution history as if it were the signed receipt
- Describing the hosted proof route as stronger than it is
- Exporting receipts before deciding who owns retention and follow-up verification
- Skipping verification language discipline when the receipt is used outside the product boundary
