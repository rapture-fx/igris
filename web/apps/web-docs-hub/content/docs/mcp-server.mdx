# MCP Server

This page documents the MCP server surface that Igris exposes through the product.

The goal is to treat MCP as part of the product contract, not as an implementation detail hidden behind generic tool calls.

---

## What The MCP Server Is For

Use the MCP server when context needs to move between agents, tools, sessions, or runtimes in a structured way.

That makes it useful for:

- shared mission state
- tool-oriented working context
- multi-agent coordination
- runtime-local or cross-runtime context exchange

If the problem is only one request deep, keep the data in the request instead. Use MCP when the context belongs to the operating environment.

## Customer Contract

The customer-facing hosted entry points are:

- `POST /v1/mcp` for request/response JSON-RPC calls
- `POST /v1/mcp/stream` for streaming MCP interactions

The product forwards those calls to the appropriate runtime MCP server where needed, so the customer can keep thinking in terms of one product surface.

## Request Shape

The MCP request body follows JSON-RPC 2.0:

```json
{
  "jsonrpc": "2.0",
  "method": "context/write",
  "params": {
    "key": "mission_state",
    "value": {
      "step": 3,
      "status": "navigating"
    }
  },
  "id": 1
}
```

## Core Method Families

The main MCP method families exposed through Igris today are:

- `context/*` for structured shared context
- `tools/*` for tool discovery and invocation

Treat the specific method contract as part of your application integration, not as an undocumented side channel.

## Integration Guidance

- keep request-local prompt data out of MCP unless it truly belongs in shared state
- prefer explicit keys and schemas for shared context
- do not mix audit evidence with working context
- use durable tasks when progress recovery matters more than context recall
