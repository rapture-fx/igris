# MCP Server

`POST /v1/mcp` is the agent-facing MCP endpoint. It is backed directly by Igris's
action, task, and runtime primitives — it is not a generic context store and it does
not forward arbitrary methods to a runtime.

Treat it as a narrow, tenant-scoped control surface: an agent can discover the
registered actions it is allowed to call, call them, and inspect the resulting runs
and evidence. Nothing else is exposed.

---

## Transport

The endpoint speaks JSON-RPC 2.0. Authentication is a tenant credential
(BetterAuth); every call is scoped to the caller's tenant.

Two methods are supported:

- `tools/list` — return the available tools and their input schemas
- `tools/call` — invoke a tool by name with `arguments`

```json
{
  "jsonrpc": "2.0",
  "id": "req_1",
  "method": "tools/list",
  "params": {}
}
```

## Tools

The server exposes exactly these tools. There are no `context/*` or `resource/*`
methods.

| Tool | Purpose |
|---|---|
| `list_actions` | List the tenant's registered actions |
| `get_action` | Fetch one registered action by `action_id` or `action_name` |
| `call_action` | Run a registered action |
| `list_runs` | List recent runs for the tenant |
| `get_run` | Fetch one run's status and proof state |
| `get_run_evidence` | Fetch a run's evidence/receipt metadata |
| `list_runtimes` | List the tenant's registered runtimes |

## Schemas Are Strict

Every tool schema is closed: `additionalProperties` is `false`. Unknown fields are
rejected rather than ignored. If you send a field a tool does not declare, the call
fails with a validation error — so send only the documented arguments.

The tenant is always taken from your credential. There is no argument you can add to
target another tenant or to bypass an action's configured target and policy; such
fields are refused.

## Calling an Action

`call_action` runs a **registered** action. You identify it by `action_id` or
`action_name` (one is required); you cannot describe an arbitrary execution graph
inline. The action definition decides the target and policy; your arguments only
supply `input`, optional `metadata`, an `idempotency_key`, and an optional
`deadline_at`.

```json
{
  "jsonrpc": "2.0",
  "id": "req_2",
  "method": "tools/call",
  "params": {
    "name": "call_action",
    "arguments": {
      "action_name": "create_ticket",
      "input": { "title": "Disk pressure on node-7" },
      "idempotency_key": "node7-disk-2026-06-10"
    }
  }
}
```

If the action targets a local runtime, the call is refused with a clear error unless
the tenant has a healthy, reachable runtime connected.

The response includes a `run_id` and an `inspect_ref` you can pass to `get_run`.

## Inspecting Runs

`get_run` and `get_run_evidence` are tenant-bound: you can only read runs owned by
your tenant. They return run status, proof state, and safe evidence metadata — not
raw request bodies, response bodies, or file contents. See
[Execution Receipts](/docs/execution-receipts) for what evidence records contain.

## Integration Guidance

- Register the actions you want agents to call; do not expect to pass raw execution
  details through MCP.
- Use an `idempotency_key` on `call_action` so a retried call does not double-run.
- Inspect outcomes with `get_run` / `get_run_evidence`; do not assume success from
  the `call_action` acknowledgement alone.
- Keep audit evidence and working prompt state separate concerns.
