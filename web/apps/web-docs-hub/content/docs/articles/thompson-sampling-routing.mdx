# Adaptive Path Selection in Igris

Path selection is an advanced part of the **Execute** stage in Igris.

The main product value is not the algorithm itself. The value is that Igris can choose a configured execution path, record what happened, and return metadata and signed records you can inspect later.

---

## Where It Fits

Use adaptive path selection when:

- you have more than one provider or execution path configured
- you want execution to react to health, latency, or policy constraints
- you need those choices recorded as part of the run

If you only call one provider directly, you may not need any of this.

---

## What The System Actually Tracks

Igris can track recent execution outcomes such as:

- provider or path used
- success or failure
- latency
- cost metadata where available

Those signals can inform later path selection. The important operational outcome is that the decision becomes part of the execution record rather than an invisible client-side guess.

---

## Advanced Strategies

Some deployments use adaptive strategies such as Thompson-sampling-style selection or other cost- or latency-oriented policies.

Treat those as advanced execution mechanisms:

- they belong under the Execute stage
- they are not the first reason to adopt Igris
- performance outcomes depend on workload, configuration, and provider behavior

Avoid assuming a benchmark or latency gain unless you have measured it in your own environment.

---

## What To Inspect After A Run

When advanced path selection is enabled, operators should inspect:

- which path or provider was chosen
- whether a fallback path was taken
- what the final execution status was
- which receipt or signed record corresponds to the run

That is where Igris differs from a thin routing proxy: execution decisions remain reviewable.
