# Security

Igris security has two distinct planes:

- **Tenant API keys** for automation and programmatic access
- **Console session cookies** for browser access to the web app

Treat those as different contracts.

---

## Authentication

### Tenant API Keys

Tenant API keys use the `igris_` prefix and are accepted in:

- `Authorization: Bearer YOUR_IGRIS_API_KEY`
- `X-API-Key: YOUR_IGRIS_API_KEY`

Best practices:

- Store tenant API keys in environment variables
- Rotate them if exposed
- Scope usage to the tenant that owns the key

```bash
export IGRIS_API_KEY="igris_abc123..."
```

### Console Sessions

The web console uses Better Auth session cookies. Those cookies are not a published bearer-token contract. Do not script console session access as generic bearer authorization headers.

### Provider Keys

Provider keys stored through the current public vault API are encrypted before storage and returned only as masked values.

## Policy And Capability Controls

A restrictive starting point in the current control-plane policy model looks like this:

```json
{
  "allow_http": false,
  "allow_shell": false,
  "allow_fs_write": false,
  "allow_external_api": false,
  "domain_allowlist": [],
  "domain_denylist": [],
  "writable_paths": [],
  "readable_paths": [],
  "violation_behavior": "terminate"
}
```

Start tight, then expand based on observed violations and actual agent requirements.

## Receipts And Verification

Customer-facing verification routes currently live on the proof API:

- `GET /proof/receipts`
- `POST /proof/receipts/verify`
- `GET /v1/proof/violations`

Example:

```bash
curl -X POST https://overture.igrisinertial.com/proof/receipts/verify \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"hash": "sha256:...", "signature": "base64:..."}'
```

Treat that hosted verification route carefully. The stronger proof-backed cryptographic verification story is demonstrated in the local proof path; the hosted route should be described according to its current stored-value comparison and proof-status behavior.

## Deployment Notes

- The local runtime can enforce its own API key with the local `auth` config
- Fleet registration is gated by a valid `IGRIS_LICENSE_KEY` plus `IGRIS_API_KEY`
- For local-only deployments, point clients directly at the runtime and keep your own storage if you need offline receipt retention

---

## Compliance

Igris is positioned to support compliance workflows, but the exact operational model depends on where you run the control plane and runtime.

- **Data residency** depends on whether you call Overture, the local runtime, or both
- **Auditability** comes from receipts, proof endpoints, and export workflows
- **Least privilege** comes from capability policy and local runtime auth

For higher-assurance deployment reviews, use the exact route and config contracts documented in the current code-backed docs, not generic platform assumptions.
