# Execution Receipts

Execution receipts are the customer-facing audit record for what ran, where it ran, and whether policy violations occurred.

---

## Current Query Surface

The current customer query surface for receipts lives in Overture:

- `GET /v1/receipts`
- `GET /v1/receipts/:id`
- `GET /v1/receipts/export`
- `GET /proof/receipts`
- `POST /proof/receipts/verify`

The current runtime build does **not** expose a public local `GET /v1/receipts` listing endpoint. If you are running fully local, consume the signed `execution_receipt` data returned in responses and store it in your own workflow if you need local retention.

---

## List Receipts

```bash
curl "https://overture.igrisinertial.com/v1/receipts?limit=50&violations_only=true" \
  -H "Authorization: Bearer YOUR_API_KEY"
```

Supported query parameters:

| Parameter | Description |
|---|---|
| `limit` | Max results, default `50`, max `500` |
| `from` | Inclusive lower timestamp bound |
| `to` | Inclusive upper timestamp bound |
| `agent_id` | Filter by agent ID |
| `violations_only` | Restrict to violating executions |

Current response shape:

```json
[
  {
    "execution_id": "exec-01HXYZ",
    "agent_id": "agent-abc",
    "runtime_id": "runtime-01",
    "tenant_id": "tenant-456",
    "timestamp_utc": "2026-03-01T12:00:00Z",
    "wall_time_ms": 312,
    "cpu_time_ms": 287,
    "memory_peak_mb": 48,
    "tool_calls": 1,
    "violation_occurred": false,
    "status": "completed",
    "receipt_hash": "sha256:a3f9...",
    "previous_hash": "sha256:b2e8...",
    "signature": "base64:...",
    "transaction_id": "txn-01HXYZ",
    "prompt_preview": "Evaluate whether to initiate..."
  }
]
```

## Export Receipts

```bash
curl "https://overture.igrisinertial.com/v1/receipts/export?format=jsonl&from=2026-03-01T00:00:00Z" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -o receipts.jsonl
```

The current export formats are:

- `jsonl` (default)
- `csv`

Current export filtering supports:

- `from`
- `to`

## Proof Verification

Use the proof endpoints when you want receipt-oriented verification views:

```bash
curl -X POST https://overture.igrisinertial.com/proof/receipts/verify \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "execution_id": "exec-01HXYZ",
    "hash": "sha256:...",
    "signature": "base64:..."
  }'
```

This endpoint compares submitted receipt values against the stored record and syncs proof status. In the current handler it does **not** perform full cryptographic signature verification by itself. Use the local proof-backed verification flow when you need the strongest demonstrated verification path today.
