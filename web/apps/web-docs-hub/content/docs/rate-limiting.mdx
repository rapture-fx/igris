# Rate Limiting

The current shipped Overture server applies a global rate limiter of **100 requests per minute** by default. Runtime binary downloads also have a dedicated **10 downloads per hour per tenant** cap.

---

## What The Hosted API Enforces

The hosted API applies:

- one shared window: `100 req/min` by default
- scoped per tenant when tenant context exists, otherwise per IP

The current middleware does **not** publish rate-limit headers on every successful response. It sets rate-limit headers only on the rejection path.

---

## 429 Response Shape

When the global limiter is exceeded, the current response looks like this:

```json
{
  "error": {
    "message": "Rate limit exceeded. Please try again later.",
    "type": "rate_limit_error",
    "code": "RATE_LIMIT_EXCEEDED"
  },
  "retry_after_seconds": 60
}
```

Headers on the rejection path include:

- `Retry-After`
- `X-RateLimit-Limit`
- `X-RateLimit-Remaining`

Do not depend on `X-RateLimit-Reset` being present on successful requests in the current build.

---

## Runtime Download Limit

Runtime archive downloads have a separate limit of `10/hour` per tenant on the control plane download surface.

This applies to:

- `GET /v1/runtime/download`
- subscribed runtime download workflows behind the cloud control plane

---

## Local Runtime Rate Limits

The local runtime auth config supports its own request controls:

```json5
{
  auth: {
    enabled: true,
    api_key: "YOUR_IGRIS_API_KEY",
    rate_limit_per_minute: 60,
    rate_limit_burst: 10
  }
}
```

| Field | Description |
|---|---|
| `rate_limit_per_minute` | Maximum local requests per minute |
| `rate_limit_burst` | Additional local burst budget |

---

## Client Guidance

- Treat `429` plus `retry_after_seconds` as the contract
- Add exponential backoff client-side
- Batch receipt exports and large history queries
- Do not assume tier-specific global limits unless they are explicitly published in a future release contract
