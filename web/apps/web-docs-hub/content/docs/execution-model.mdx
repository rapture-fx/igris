# Execution Model

The Igris execution model is:

1. **Request**
2. **Execute**
3. **Verify**

Everything else on this page is a more detailed explanation of those three stages.

---

## Request

Request is how work enters Igris.

That can be an OpenAI-compatible call, a task-oriented request, or another documented surface. The key idea is consistency: the request enters one execution system, not a collection of unrelated product identities.

At request time, Igris establishes the context that matters for the run:

- identity and tenant scope
- input payload and parameters
- capability expectations
- applicable limits or policy boundaries

## Execute

Execution is where the request becomes governed work.

During execution, Igris can:

- apply capability and policy checks
- enforce budgets and other boundaries
- capture execution events and state
- run on the hosted or runtime-backed path configured for the workload
- record violations or failure outcomes instead of hiding them

This is the layer that turns a plain model response into an inspectable run.

### Boundaries

Typical execution boundaries include:

| Boundary | What it restricts |
|---|---|
| Capability gates | What the run is allowed to do |
| Token or resource limits | How much work the run can consume |
| Time limits | How long execution is allowed to continue |
| Tool restrictions | Which external actions are allowed |

If execution exceeds an allowed boundary, that outcome should be recorded as part of the run.

## Verify

Verification is how you inspect what happened after execution.

Depending on the path, Igris can return or persist:

- execution metadata
- signed execution envelopes
- signed execution receipts
- receipt hashes
- proof-status information

That is what makes the system useful for review, governance, and post-run analysis.

## Signed Records

The model is not complete until the run produces something you can inspect later.

In Igris terms, that can include:

- the execution envelope for the run context
- the execution receipt for the final record
- hash-linked receipt material for downstream audit workflows

Use [Execution Receipts](/docs/execution-receipts) and [Verification](/docs/verification) for the public-facing receipt and proof workflows.

## Deployment Modes Fit Under The Same Model

Hosted, local, and hybrid setups all fit under the same execution model:

- the request still enters through Igris
- execution still runs under boundaries
- verification still depends on the records produced by the run

The deployment mode changes where execution happens, not what product the user is learning.

## What To Treat Carefully

- Real provider-backed execution is supported and configurable, but proof claims should follow [Proof Status](/docs/proof-status).
- Local GGUF fallback and checkpoint recovery should not be treated as universally proven behaviors unless you have the right artifact for the scenario.
- Advanced routing strategies are part of the broader platform, but they are not the first concept to teach when explaining execution.
