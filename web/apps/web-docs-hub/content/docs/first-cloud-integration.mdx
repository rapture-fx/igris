# First Hosted Integration

Use this workflow when you want the shortest path from the Request -> Execute -> Verify model into a provider-backed hosted integration.

Hosted execution is one deployment mode for Igris. It is a good fit when the team wants to start with a managed API surface, keep the application contract simple, and prove that governed execution is useful before adding local runtime infrastructure.

The basic sequence is:

1. Create a tenant API key
2. Add at least one provider key
3. Send a request through the hosted Igris API surface
4. Inspect execution metadata and decide whether you need deeper Igris-native features

---

## 1. Create A Tenant API Key

Create one tenant API key for the environment that will call the hosted surface. Treat it like any other production secret and keep it in your standard secret store.

- [Trial & Billing →](/docs/trial-billing)
- [API Authentication →](/docs/api-reference/authentication)

## 2. Add A Provider Key

Hosted execution depends on provider credentials stored in the Igris vault. For customer traffic today, use `openai` or `anthropic`.

```bash
curl -X POST https://overture.igrisinertial.com/v1/vault/keys \
  -H "Authorization: Bearer YOUR_IGRIS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "openai",
    "key_name": "production",
    "api_key": "YOUR_OPENAI_KEY"
  }'
```

## 3. Send A Hosted Request

The simplest application-facing path is OpenAI-compatible:

```typescript
import OpenAI from 'openai';

const client = new OpenAI({
  baseURL: 'https://overture.igrisinertial.com/v1',
  apiKey: process.env.IGRIS_API_KEY,
});

const response = await client.chat.completions.create({
  model: 'gpt-4o-mini',
  messages: [{ role: 'user', content: 'Summarize the latest service status' }],
});

console.log(response.choices[0].message.content);
```

This is still the same product model:

- **Request** through one Igris surface
- **Execute** on the hosted provider-backed path you configured
- **Verify** using metadata, receipts, and proof-oriented pages when the workflow needs them

## 4. Inspect What You Need Next

Stay on the hosted OpenAI-compatible path when you want:

- the least integration overhead
- broad SDK portability
- provider-backed execution without local deployment work

Move deeper into Igris surfaces when you need:

- receipt-oriented workflows
- richer execution metadata
- runtime participation
- local or hybrid deployment

## Proof Language For Hosted Execution

Be precise about what is proven:

- Hosted provider-backed execution is a supported deployment mode.
- Real provider paths are configurable and wired through the product surfaces.
- The strongest proof-backed walkthrough in these docs is still the local verified run, not a previously captured real-provider proof artifact.

Use [Proof Status](/docs/proof-status) if you need to separate proven behavior from supported but not-yet-proven paths.

## Common Mistakes

- Treating hosted execution like a different product instead of one deployment mode
- Forgetting to add a provider key before sending hosted traffic
- Starting with advanced deployment work before proving the hosted path fits the use case
- Assuming provider-backed support means every provider workflow is already proven in your environment
