# Approvals

Most registered actions run as soon as policy allows. Some should not run without a
human decision first: moving money, deleting data, anything irreversible or out of an
agent's normal scope. For those actions, Igris pauses the run and waits for a reviewer
to approve or reject it. Approval is part of the controlled path an action takes from
request to review, not a bolt-on. The run is only dispatched after a reviewer approves
it, and the decision is recorded on the run.

---

## When A Run Needs Approval

Whether an action needs approval is a property of the registered action, not of each
call. An action requires approval when it is registered with the `Human-gated` policy
preset, or with `approval_required: true`. See [Policy and Approvals](/docs/policy)
for how presets map to behavior.

When an agent runs a human-gated action through `POST /v1/actions/:name/run` (or MCP
`call_action`), Igris evaluates policy, records the run, and then pauses instead of
dispatching. The run response is `409` with `error: approval_required` and the run id:

```json
{
  "run_id": "018f4a2b-3c1e-7a2d-9b8f-4d5e6f7a8b9c",
  "task_id": "018f4a2b-3c1e-7a2d-9b8f-4d5e6f7a8b9c",
  "status": "approval_required",
  "error": "approval_required",
  "proof_status": "pending"
}
```

This is an expected pause, not a failure. The run holds in `approval_required` until a
reviewer decides. It does not time out on its own and it does not execute in the
meantime. Treat `409 approval_required` in your client as "waiting for a human", not as
an error to retry.

The starter Action Pack includes `demo.needs_approval`, a human-gated `mock_demo`
action you can use to see this flow end to end without touching a real target. See
[First Agent Onboarding](/docs/first-agent-onboarding).

## Finding Runs That Are Waiting

You already have the run id from the `409` response. To follow a run or confirm it is
still waiting, inspect it:

```bash
curl https://overture.igrisinertial.com/v1/actions/runs/018f4a2b-3c1e-7a2d-9b8f-4d5e6f7a8b9c \
  -H "Authorization: Bearer $IGRIS_API_KEY"
```

A run that is waiting reports `status: approval_required`. Agents connected over MCP can
read the same state with the `get_run` tool. In the console, runs waiting for a decision
appear in the run view with Approve and Reject controls.

## Approving A Run

Approval continues the controlled path: the run is dispatched to a runtime and executes,
then produces the same recovery and proof records as any other run.

```bash
curl -X POST \
  https://overture.igrisinertial.com/v1/actions/runs/018f4a2b-3c1e-7a2d-9b8f-4d5e6f7a8b9c/approve \
  -H "Authorization: Bearer $IGRIS_API_KEY"
```

Response:

```json
{
  "run_id": "018f4a2b-3c1e-7a2d-9b8f-4d5e6f7a8b9c",
  "task_id": "018f4a2b-3c1e-7a2d-9b8f-4d5e6f7a8b9c",
  "status": "dispatched",
  "proof_status": "pending",
  "decision": "approved",
  "approved_by": "usr_2f9a1c7b"
}
```

Approve takes no request body. The approver recorded on the run is the authenticated
principal behind your credential; it cannot be set from the request body. After approval
the run behaves like a normal run: poll `GET /v1/actions/runs/:id` to follow it to
completion and check `proof_status`.

Approval is a real gate with two properties worth knowing:

- **It dispatches at most once.** If two reviewers approve the same run at the same
  time, or the same reviewer approves twice, only the first call dispatches. Later calls
  return `409 not_awaiting_approval`. A run can never be double-dispatched by a repeated
  approve.
- **It is safe to retry when a runtime is missing.** For actions that run on your own
  connected runtime, if no runtime is available at approval time the call returns
  `503 runtime_unavailable` and the run stays in `approval_required`. Reconnect a runtime
  and approve again.

## Rejecting A Run

Rejection closes the run without executing it. The pending side effect does not happen.

```bash
curl -X POST \
  https://overture.igrisinertial.com/v1/actions/runs/018f4a2b-3c1e-7a2d-9b8f-4d5e6f7a8b9c/reject \
  -H "Authorization: Bearer $IGRIS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"reason": "target account is out of scope for this agent"}'
```

Response:

```json
{
  "run_id": "018f4a2b-3c1e-7a2d-9b8f-4d5e6f7a8b9c",
  "task_id": "018f4a2b-3c1e-7a2d-9b8f-4d5e6f7a8b9c",
  "status": "failed",
  "decision": "rejected",
  "rejected_by": "usr_2f9a1c7b",
  "dispatched": false
}
```

The `reason` field is optional free text. Record one so the decision is clear when
someone reviews the run later. A rejected run is a terminal outcome: it is closed with
the rejection decision and reason, and it is never dispatched. The same
awaiting-approval check that protects approval protects rejection, so a run that has
already been approved or rejected cannot be rejected again (`409 not_awaiting_approval`).

Rejection does not resume. To run the action again, resolve whatever made it wrong, then
submit a new run through the Actions gateway. The rejected run stays on record.

## What The Decision Leaves Behind

Every human-gated run carries its decision on the run record: whether it was approved or
rejected, who decided, and the rejection reason when there is one. Approved runs continue
to execution and produce a receipt you can verify like any other run. See
[Runs and Recovery](/docs/durable-tasks) for run lifecycle and
[Proof and Receipts](/docs/execution-receipts) for what verification covers.

---

## Distinguishing The Two Approval Routes

The routes above, `POST /v1/actions/runs/:id/approve` and
`POST /v1/actions/runs/:id/reject`, are the approval routes for durable action runs:
runs created with `POST /v1/actions/:name/run`, `POST /v1/actions/run`, or MCP
`call_action`. Use these routes for action approvals.

Igris also exposes an older approval route under the execution inspection surface
(`/v1/execution/runs/:id/approve`). That route belongs to a separate execution-lineage
view and is not the path for approving durable action runs. If you are working with the
Actions gateway, use the action routes on this page.

## Best Practices

**Reserve approval for what needs it.** Human-gated actions are the ones where a wrong
call is expensive: irreversible changes, high-value targets, actions outside an agent's
normal scope. Keep routine actions on `Safe automation` so reviewers only see decisions
that matter.

**Record a reason for every rejection.** Even routine rejections are more useful later
when the run record says why.

**Do not resubmit blindly.** A rejected action was rejected for a reason. Fix the
underlying issue, a policy grant, a wrong target, an out-of-scope request, before
submitting a new run.

**Treat `approval_required` as a normal state in your client.** An agent that calls a
human-gated action should handle `409 approval_required` by surfacing the run for review,
not by retrying or erroring out.
