# Execution Flow

This page is the detailed version of Request -> Execute -> Verify.

Use it when you already understand the product model and want the more concrete lifecycle of a run.

---

## Lifecycle Overview

```text
1. Request enters Igris
        |
        v
2. Igris authenticates, scopes, and prepares execution
        |
        v
3. Execution runs on the configured hosted or runtime-backed path
        |
        v
4. Igris records execution metadata and outcome details
        |
        v
5. Receipt-oriented records and verification surfaces become available
```

## 1. Request Intake

The lifecycle starts when the application sends work through a documented Igris surface.

At intake, Igris determines the context for the run:

- who is making the request
- which tenant or deployment context applies
- what inputs and parameters were supplied
- which boundaries and policies matter for this run

## 2. Execution Preparation

Before the main work runs, Igris prepares the execution path.

That can include:

- authentication and tenant scoping
- policy or capability checks
- resource and budget checks
- choosing the hosted or runtime-backed path that should own execution

This is where the run becomes governed work rather than an unstructured provider call.

## 3. Execution

Execution happens on the configured path for the workload.

### Hosted path

When the workload stays on the hosted path, Igris coordinates the provider-backed execution and returns the resulting output plus the metadata relevant to that run.

### Runtime-backed path

When the workload uses runtime participation, the runtime owns the execution step and can produce the execution artifacts associated with that path.

### Failure-path language

Igris is designed to make failure paths visible, but you should still be precise:

- some runtime-backed proof paths are demonstrated locally
- some broader failover or recovery stories are supported in architecture but not yet proven in every environment

Use [Proof Status](/docs/proof-status) when you need to distinguish those cases.

## 4. Execution Events And Outcome

After or during execution, the workflow can expose:

- route decisions
- provider or runtime labels
- usage and timing details
- execution-state outcomes
- receipt-oriented material

This is the point where the flow becomes inspectable instead of disappearing behind a plain text response.

## 5. Receipt And Verification Layer

When the run needs post-execution review, move into the verification layer:

- inspect receipt-oriented records
- compare stored values where the hosted proof route is appropriate
- use the local verified run when you need the strongest demonstrated signature and hash checks

Relevant pages:

- [Execution Receipts](/docs/execution-receipts)
- [Verification](/docs/verification)
- [Receipts and Audit Workflow](/docs/receipts-audit-workflow)

## A Simple Way To Read The Flow

If you are explaining Igris to another engineer, the shortest honest version is:

1. send a request through Igris
2. let Igris execute it under boundaries
3. inspect the records the run produced

Everything else is detail layered underneath that lifecycle.
