# Cloud Coordination

Cloud coordination is the hosted part of the Igris execution system.

Its job is to coordinate provider-backed execution, expose customer-facing management surfaces, and connect runtimes into the broader execution model when hybrid workflows are enabled.

That is useful when you want:

- a stable hosted entry path for applications
- provider-backed execution without custom client-side routing logic
- runtime lifecycle and fleet-oriented operator surfaces
- customer-facing receipt and audit workflows

---

## What Hosted Coordination Does

Hosted coordination can cover:

- application-facing request entry
- provider-backed execution setup
- runtime registration and lifecycle surfaces
- receipt and proof-oriented query surfaces
- account, policy, and key-management workflows

This is part of one execution system. It should not be read as a separate product introduction.

## Hosted Request Entry

For many teams, the first hosted path is the OpenAI-compatible surface:

```text
https://overture.igrisinertial.com/v1
```

That keeps the application contract simple while letting Igris own the execution path behind it.

## Provider Configuration

Hosted execution depends on provider credentials stored through the vault API.

For customer traffic today, use `openai` or `anthropic`.

```bash
curl -X POST https://overture.igrisinertial.com/v1/vault/keys \
  -H "Authorization: Bearer YOUR_IGRIS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "openai",
    "key_name": "production",
    "api_key": "YOUR_OPENAI_KEY"
  }'
```

Provider-backed execution is configurable and supported. Proof claims about specific real-provider flows should still follow [Proof Status](/docs/proof-status).

Use the endpoint pages for the exact request contracts:

These routes matter for operations and hybrid deployment. They are not the first concept to teach when introducing the product.

## Receipt And Audit Surfaces

The hosted layer also exposes the customer-facing receipt and proof-oriented query routes:

- `GET /v1/receipts`
- `GET /v1/receipts/:id`
- `GET /v1/receipts/export`
- `GET /proof/receipts`
- `POST /proof/receipts/verify`

Use those routes for hosted audit workflows, while keeping the verification semantics precise. The hosted proof-verify route is useful for stored-value comparison and proof-status sync, not as a blanket claim of full public cryptographic verification.
