# Hybrid Deployment Workflow

Use this workflow when one Igris execution model needs to span hosted and local environments.

Hybrid deployment is still one product story:

- **Request** enters through a stable application-facing Igris surface
- **Execute** can involve hosted coordination and runtime-backed execution
- **Verify** stays tied to the same records, receipts, and inspection workflows

This model is useful when you care about:

- governance across hosted and local environments
- running execution closer to devices or private infrastructure
- clearer failure-path handling between application traffic and runtime operations
- verification-ready records even when execution topology is mixed

---

## 1. Keep One Application-Facing Contract

In most hybrid setups, the application still points at the hosted base URL:

```text
https://overture.igrisinertial.com/v1
```

That keeps the application contract stable while allowing runtime participation underneath.

## 2. Start Runtimes With The Right Registration Context

Hybrid deployment only works when the runtime can start and register correctly.

```bash
export IGRIS_LICENSE_KEY="YOUR_LICENSE_KEY"
export IGRIS_API_KEY="YOUR_IGRIS_API_KEY"
igris-runtime serve
```

This is the operational step that makes runtime-backed participation possible. It does not create a second product surface for the application team.

## 3. Verify Hosted And Runtime Health Separately

Check both sides of the system deliberately:

- hosted API calls succeed with your tenant API key
- the runtime answers `http://localhost:8080/v1/health`
- runtime registration and visibility succeed where your workflow depends on them

Hybrid works best when execution traffic and runtime operations are both observable.

## 4. Decide What Must Stay Hosted Versus Local

Use hosted coordination when you want:

- the simplest application-facing entry path
- provider-backed execution without device-local routing decisions in the client
- centralized operator workflows

Use runtime-backed execution when you want:

- locality
- device-level governance
- execution near private infrastructure or tools

The important point is that the workflow still belongs to one execution system.

## 5. Treat Failure Paths Carefully

Hybrid deployment is often adopted because teams care about failure handling, but you should be disciplined about proof language:

- hybrid participation is real
- runtime registration and coordination surfaces are real
- not every failover or recovery story should be described as proven unless you have the corresponding proof artifact

Use [Proof Status](/docs/proof-status) when the docs or rollout plan need to separate supported architecture from demonstrated behavior.

## Common Mistakes

- Explaining hybrid as if it were two different products glued together
- Mixing runtime lifecycle traffic with ordinary application requests
- Assuming all failover scenarios are already proven in your environment
- Pointing clients directly at coordination or fleet routes when the application should stay on the main API surface
