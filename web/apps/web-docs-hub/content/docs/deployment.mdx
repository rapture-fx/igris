# Deployment

Choose your deployment mode based on where execution should run.

Igris is one execution system with multiple deployment modes:

- **hosted** when provider-backed execution through the managed surface is enough
- **local** when work should run closer to your machine or device
- **hybrid** when hosted coordination and runtime participation both matter

The deployment choice changes where execution happens. It does not create separate products.

---

## Hosted Deployment

Use hosted deployment when you want the fastest provider-backed path with the least operational overhead.

```python
from openai import OpenAI

client = OpenAI(
    base_url="https://overture.igrisinertial.com/v1",
    api_key="your-api-key"
)
```

Hosted deployment is a good fit when you want:

- managed API entry
- provider-backed execution
- simpler onboarding
- customer-facing receipt and audit surfaces without local runtime operations

Proof claims for specific real-provider paths should still follow [Proof Status](/docs/proof-status).

## Local Deployment

Use local deployment when execution should happen closer to the environment doing the work.

Typical reasons:

- device or infrastructure locality
- local tool or workflow integration
- low-connectivity or offline-sensitive operation
- runtime-side governance near the workload

Start the runtime on your own infrastructure and point the client at the runtime base URL when the request belongs there.

## Hybrid Deployment

Use hybrid deployment when you want one application-facing contract while allowing runtime participation underneath.

This mode is useful when you need:

- a hosted entry path for applications
- runtime-backed execution in selected environments
- operator visibility into registered execution environments

Keep the proof language careful:

- hybrid architecture is supported
- not every failover or recovery behavior should be described as proven without the matching artifact

See [Hybrid Deployment Workflow](/docs/hybrid-deployment-workflow) for the staged operator view.

## Local Models And Fallback Language

Local model configuration is part of the deployment story, but language here should stay disciplined:

- local execution is real
- local fallback paths exist in the product model
- failure-to-local-model proof should follow [Proof Status](/docs/proof-status) before being described as proven behavior

## Verifying A Deployment

After you deploy, verify the mode you chose:

- hosted mode: confirm requests succeed through the hosted base URL
- local mode: confirm the runtime answers health checks and accepts local requests
- hybrid mode: confirm both hosted access and runtime registration behave as expected

Then move into run inspection and verification workflows, not just health checks.

## Common Deployment Issues

- Treating hosted, local, and hybrid as different products instead of deployment modes
- Assuming local fallback or hybrid failover is universally proven without checking the proof status
- Mixing hosted and local base URLs without being explicit about which execution surface owns the request
- Expanding deployment scope before verifying the first environment slice
