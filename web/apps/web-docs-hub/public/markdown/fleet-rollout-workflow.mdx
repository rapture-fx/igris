# Fleet Rollout Workflow

Use this workflow when you want to introduce runtime-backed execution environments in stages instead of turning on broad rollout all at once.

The goal is simple:

1. start small
2. observe execution behavior
3. verify the records that matter
4. expand only after the first slice is stable

This page is about staged rollout of execution environments.

---

## 1. Start With A Small Environment Set

Before expanding rollout, make sure each target environment can:

- start cleanly
- register successfully
- remain visible through heartbeat reporting
- execute the workload shape you care about

If those basics are not healthy, rollout is the wrong next step.

## 2. Observe Execution Before Expanding

Do not treat rollout as a blind infrastructure action. Use the first slice to inspect:

- whether environments stay registered
- whether requests route the way you expect
- whether execution events and receipts remain available
- whether customer-facing traffic is unaffected

This is the practical operator version of Request -> Execute -> Verify.

## 3. Roll Configuration Deliberately

If you use config-push surfaces, separate configuration changes from binary updates whenever possible.

That makes it easier to answer:

- did the environment change break execution behavior
- did the binary change introduce the issue
- which step should be rolled back first

Config-push surfaces exist, but broad rollout success should still be described carefully unless you have reproducible evidence for the exact pattern you are using.

## 4. Expand In Stages

A safe rollout sequence looks like:

1. one environment or a small canary group
2. inspect runtime visibility and execution behavior
3. check receipts or proof-oriented inspection where the workflow depends on them
4. expand to the next slice only after the first slice is stable

Avoid language that implies failover or recovery is already proven across the whole environment set.

## 5. Keep Rollback Simple

Plan rollback before expansion:

- keep the previous known-good runtime version available
- avoid mixing config changes and binary changes in the same rollout stage
- use staged expansion so rollback scope stays small

Rollback should be an explicit operator action, not an assumption hidden behind marketing language.

## Common Mistakes

- Expanding rollout before checking the first slice for stable registration and execution behavior
- Rolling config and binary changes together without a reason
- Assuming visible environments imply proven failover or broad recovery behavior
- Treating update surfaces as proof of end-to-end OTA readiness
