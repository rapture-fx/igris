# History & Alerts

History and alerts are part of the **Verify** stage of Igris.

Use them when you need to inspect what happened after a run, understand execution outcomes across time, or follow up on unusual behavior.

This page is about execution events and run inspection, not about claiming a complete observability platform.

---

## What Operators Can Inspect

After a run, operators may want to inspect:

- execution events
- run metadata
- timing and usage summaries
- alert state for violation-oriented follow-up
- whether a receipt-oriented workflow should be retrieved next

History helps you answer what happened over time. Receipts help you answer what record should be treated as the audit artifact.

## Execution Events

### GET /v1/history/events

Returns execution-history events for the current tenant.

```bash
curl "https://overture.igrisinertial.com/v1/history/events?range=last_24h&limit=50" \
  -H "Authorization: Bearer YOUR_API_KEY"
```

Supported query parameters:

| Parameter | Description |
|---|---|
| `range` | Window selector such as `last_1h`, `last_24h`, `last_7d`, `1h`, `24h`, `7d` |
| `limit` | Max results, up to 2000 |
| `agent_id` | Filter by agent ID |
| `device_id` | Filter by runtime or device ID |

Response shape:

```json
[
  {
    "id": "lineage-01HXYZ",
    "execution_id": "exec-01HXYZ",
    "agent_id": "agent-abc",
    "device_id": "runtime-01",
    "timestamp": "2026-03-01T12:00:00Z",
    "duration_ms": 312,
    "event_type": "execution_completed",
    "severity": "info",
    "message": "Execution completed successfully"
  }
]
```

Use this when you want the timeline view of the run.

## Metrics

### GET /v1/history/metrics

Returns summary information plus throughput and recent metric events.

```bash
curl "https://overture.igrisinertial.com/v1/history/metrics?range=last_24h" \
  -H "Authorization: Bearer YOUR_API_KEY"
```

Use this surface for operational summaries, not as a substitute for execution receipts.

## Alerts

### GET /v1/history/alerts

Returns alert state for follow-up workflows such as policy-violation review.

```bash
curl "https://overture.igrisinertial.com/v1/history/alerts?range=last_24h&limit=20" \
  -H "Authorization: Bearer YOUR_API_KEY"
```

Supported query parameters:

| Parameter | Description |
|---|---|
| `range` | Window selector such as `last_24h` |
| `limit` | Max results, up to 1000 |

Alert actions:

- `POST /v1/history/alerts/:id/acknowledge`
- `POST /v1/history/alerts/:id/resolve`
- `POST /v1/history/alerts/:id/escalate`

## How History Fits With Receipts

Use history when you want to inspect the run across time.

Use receipts when you need:

- the signed or hash-linked record
- exportable audit evidence
- proof-oriented follow-up

That distinction matters. Execution history is not the same thing as the receipt artifact.

## Common Mistakes

- Treating history as the audit artifact instead of retrieving the receipt-oriented record
- Assuming summary metrics alone explain what happened during execution
- Describing alerts as a complete observability or incident-response platform
