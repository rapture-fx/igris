# Governance

Governance in Igris starts with the Request -> Execute -> Verify model.

- **Request** defines what work is being asked for and under which context.
- **Execute** applies permissions, boundaries, and runtime checks while the work runs.
- **Verify** makes the resulting events and signed records available for inspection later.

This page is about the practical controls around execution, not about broad unsupported governance claims.

---

## What Governance Covers

Governance answers four operator questions:

1. what was requested
2. what the run was allowed to do
3. what happened during execution
4. what record is available afterward

That maps directly to:

- permissions and capability checks
- execution boundaries
- execution events and outcome state
- signed records and receipt-oriented inspection

## Before Execution: Permissions And Scope

Before the main work runs, Igris can apply controls such as:

- tenant or deployment scope
- capability grants
- allowed tools or access paths
- duration or resource expectations

This is the part of governance that decides whether the request is allowed to become execution at all.

## During Execution: Boundaries And Events

While the run is active, governance is about keeping execution inside its declared boundaries and making the outcome inspectable.

Examples include:

- capability checks during tool or action attempts
- resource boundaries such as duration or token limits
- recording violations or rejected actions
- surfacing execution events that help operators understand what happened

That is why governance belongs to execution itself, not just to a static policy document.

## After Execution: Signed Records

Governance is only useful if the result can be checked later.

Depending on the path, Igris can return or persist:

- execution metadata
- signed execution envelopes
- signed execution receipts
- receipt-oriented audit records

## Capability Boundaries

Governance often starts with capability scope.

Typical controls include:

| Control | What it governs |
|---|---|
| Tool permissions | Which external actions are allowed |
| Domain or path limits | Where an execution may reach |
| Resource limits | How much work the execution may consume |
| Review points | Which actions should require operator attention |

The important point is not the label of the control. The important point is that the run is bounded and the result is inspectable afterward.

## Review And Follow-Up

After a run, governance becomes an operator review workflow:

- inspect history or execution events
- retrieve receipt-oriented records
- verify what the available proof surfaces can actually confirm
- adjust policy or permissions if the run exceeded the intended scope

## What To Avoid Claiming

This page should not be read as a claim that Igris is already a full generalized compliance platform. Keep the scope precise:

- governance around execution boundaries is real
- signed records and verification-ready receipts are part of the product story
- proof language should still follow [Proof Status](/docs/proof-status) for stronger claims
