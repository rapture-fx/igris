# First Agent Onboarding

Use this path when a real agent or MCP client needs to run its first Igris action.
The fastest supported path is **templates-first**: install the CLI, generate an agent
template, install the starter Action Pack, run one registered action with an
idempotency key, then inspect the run and evidence.

## 0. Install An Agent Template

Pick the template that matches your agent environment:

```bash
igris templates list
igris templates install claude-code    # Claude Code MCP
igris templates install codex          # terminal / Codex-style agents
igris templates install cursor         # Cursor MCP or CLI fallback
igris templates install custom-agent   # REST or MCP for any agent
```

Files land in `.igris/templates/<name>/` by default. Use `--print` to preview
without writing files. Verify when credentials are ready:

```bash
igris templates verify claude-code
```

See [Agent Templates](/docs/agent-templates) for all options. Templates generate
local config only — they use the same CLI, REST, and MCP execution path as the
steps below.

Do not start by sending raw execution graphs. `POST /v1/tasks/submit` is an
advanced durable-task API for custom workflows; first agents should call
registered actions through REST, CLI, or MCP.

## Required Values

Set these locally. Do not print secret values in logs or support tickets.

```bash
export IGRIS_API_URL="https://overture.igrisinertial.com"
export IGRIS_API_KEY="igris_..."
export IGRIS_IDEMPOTENCY_KEY="starter-echo-$(date +%Y%m%d%H%M%S)"
```

Run the readiness doctor before wiring the agent:

```bash
./scripts/igris_doctor.sh
```

The doctor checks required env names, API reachability, API-key acceptance on
safe endpoints, MCP `tools/list` when credentials are available, optional MCP
config JSON, runtime install metadata, optional local-runtime reachability, and
suggests `igris templates install <name>` when MCP config is missing an Igris
bridge. It never echoes the API key.

## 1. Install The CLI

Install the Igris CLI (`igris` / `igris-runtime`) from your environment's
installer, then verify the key:

```bash
igris auth login --api-url "$IGRIS_API_URL"
```

## 2. Register Your Agent Identity

Register the agent in your tenant before the first run so Igris can attribute
runs safely. Use a stable name per environment (for example `claude_code_agent`).

```bash
igris agents register \
  --name claude_code_agent \
  --agent-type claude_code \
  --template-name claude-code \
  --api-url "$IGRIS_API_URL"
```

REST equivalent:

```bash
curl -sS -X POST "$IGRIS_API_URL/v1/agents" \
  -H "Authorization: Bearer $IGRIS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "claude_code_agent",
    "agent_type": "claude_code",
    "template_name": "claude-code",
    "description": "Claude Code agent for starter onboarding"
  }'
```

Pass `agent_id` or `agent_name` on action runs and MCP `call_action` so the
response and run detail include a safe `agent` object. Unknown agents are
rejected; do not send `tenant_id` in the body.

## 3. Install The Starter Action Pack

The starter pack registers three safe `mock_demo` actions. No external provider
credentials are required.

```bash
igris packs list --api-url "$IGRIS_API_URL"
igris packs install starter --api-url "$IGRIS_API_URL"
```

REST equivalents:

```bash
curl -sS "$IGRIS_API_URL/v1/action-packs" \
  -H "Authorization: Bearer $IGRIS_API_KEY"

curl -sS -X POST "$IGRIS_API_URL/v1/action-packs/starter/install" \
  -H "Authorization: Bearer $IGRIS_API_KEY"
```

See the API reference for request shapes and status codes:
[GET /v1/action-packs](/docs/api-reference/action-packs/get-v1-action-packs) and
[POST /v1/action-packs/:name/install](/docs/api-reference/action-packs/post-v1-action-packs-name-install).

Installed actions:

| Action | Purpose |
|---|---|
| `demo.echo` | Happy-path echo through `mock_demo` |
| `demo.fail_once` | Simulated first-attempt failure for recovery visibility |
| `demo.needs_approval` | Pauses at `approval_required` |

Pack manifests live at `actionpacks/starter/manifest.json` in the repo. They
contain no secrets. Install registers actions only — it does not execute raw
tasks or call external providers.

## 4. Run The First Action

```bash
igris actions run demo.echo \
  --api-url "$IGRIS_API_URL" \
  --input '{"message":"first agent run"}' \
  --idempotency-key "$IGRIS_IDEMPOTENCY_KEY"
```

Equivalent REST call:

```bash
curl -sS -X POST "$IGRIS_API_URL/v1/actions/demo.echo/run" \
  -H "Authorization: Bearer $IGRIS_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $IGRIS_IDEMPOTENCY_KEY" \
  -d '{
    "input": { "message": "first agent run" },
    "idempotency_key": "'"$IGRIS_IDEMPOTENCY_KEY"'"
  }'
```

Expected success shape: a `run_id` or `task_id`, `status`, and `proof_status`.
The response must not echo Authorization headers, cookies, secret values, or raw
runtime key material.

Retry the same command with the same idempotency key. It should return the same
logical run instead of creating a duplicate side effect.

Inspect the run:

```bash
igris runs inspect "$RUN_ID" --api-url "$IGRIS_API_URL"
```

## 5. Connect Claude Code With MCP

Claude Code uses an MCP server entry. Use the Igris CLI MCP bridge on stdio; do
not point Claude at the runtime proxy surface.

Example config shape:

```json
{
  "mcpServers": {
    "igris": {
      "command": "igris",
      "args": ["mcp", "serve", "--api-url", "https://overture.igrisinertial.com"],
      "env": {
        "IGRIS_API_KEY": "igris_..."
      }
    }
  }
}
```

After connecting, ask Claude Code to list tools. It should see:

- `list_actions`
- `call_action`
- `get_run`
- `get_run_evidence`

Then call:

```json
{
  "action_name": "demo.echo",
  "input": { "message": "first agent run from Claude Code" },
  "idempotency_key": "starter-echo-claude-001"
}
```

## 6. Use Codex, Cursor, Or Terminal Agents

Terminal-based agents can use the CLI or REST commands above directly. If the
agent can invoke shell commands, give it only:

- the action name (`demo.echo` after starter pack install)
- the input schema (`{"message": "..."}`)
- the idempotency key rule
- `igris runs inspect <run_id>`

For MCP-capable terminal agents, use the same `call_action` contract as Claude
Code. The agent should not send `tenant_id`, `task_definition`, `runtime_id`,
`runtime_endpoint`, raw bodies, ciphertext, nonces, or key material; those fields
are rejected.

## 7. Custom Agents

Custom agents should call the Actions HTTP API:

```bash
curl -sS -X POST "$IGRIS_API_URL/v1/actions/demo.echo/run" \
  -H "Authorization: Bearer $IGRIS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "input": { "message": "first custom-agent run" },
    "idempotency_key": "starter-echo-custom-001",
    "metadata": {
      "agent_id": "custom-agent-local",
      "user_id": "operator"
    }
  }'
```

Use `GET /v1/actions/runs/:id`, MCP `get_run`, MCP `get_run_evidence`, or
`igris runs inspect` to confirm the result. Treat `call_action` acceptance as
"run accepted", not "side effect completed".

## Stop Conditions

Stop and fix setup before continuing if any of these happen:

- unauthenticated requests do not return `401`
- invalid API keys reveal tenant existence
- `call_action` accepts unknown or raw execution fields
- a retry with the same idempotency key creates a second side effect
- a local-runtime action runs while no runtime is healthy and routable
- proof is shown as signed when evidence is absent
- any secret, token, cookie, private URL, raw body, or key material appears in output
