# Human-in-the-Loop Approvals

Human-in-the-loop (HITL) approval pauses an execution run before it completes a high-stakes action. A reviewer must explicitly approve or reject the run before execution continues. The full approval event — who made the decision, when, and why — is recorded in the signed execution receipt and cannot be altered after the fact.

---

## How Executions Get Paused for Review

The execution engine evaluates review triggers as each run progresses. Triggers are configured in your policy and can match on tool call targets, output classifications, capability combinations, or custom conditions.

When a trigger fires, the run transitions from RUNNING to **PAUSED** with `pause_reason: human_review_required`. The run holds open in that state indefinitely — it does not time out and does not progress — until a human makes a deliberate approve or reject decision.

The execution envelope remains intact while the run is paused. Resources are reserved and the agent's context is preserved. Once a decision is made, the run either continues (approve) or terminates (reject) from exactly the point where it was paused.

---

## Finding Runs Waiting for Approval

Query paused runs via the API:

```bash
curl "https://overture.igrisinertial.com/v1/execution/runs?status=PAUSED" \
  -H "Authorization: Bearer YOUR_API_KEY"
```

Response:

```json
[
  {
    "execution_id": "exec-01HXYZ",
    "agent_id": "agent-abc",
    "status": "PAUSED",
    "pause_reason": "human_review_required",
    "paused_at": "2026-03-31T10:14:22Z",
    "prompt_preview": "About to POST to https://payments.example.com/disburse with amount: 4500",
    "runtime_id": "runtime-01"
  }
]
```

The `prompt_preview` field is a brief description of what the execution was about to do at the point it was paused. It is generated by the execution engine and is not the raw model input — it is a structured summary of the pending action, designed to give a reviewer enough context to make an informed decision.

## Reviewing in the Console

The **Execution Runs** page in the console shows all paused runs in a dedicated review queue at the top of the list. Each row shows a **Review** badge and the time the run has been waiting.

Click a paused run to open its detail panel. You will see:

- **Prompt preview** — the pending action description
- **Agent ID** — which agent initiated this run
- **Pause reason** — always `human_review_required` for HITL items
- **Paused at** — timestamp of when the run entered the queue

Review the prompt preview carefully. Consider whether the described action is within the scope of what this agent should be doing, consistent with the context that initiated the run, and aligned with your operational policy.

## Approving a Run

Approval releases the run from its paused state. It resumes immediately as RUNNING and continues from where it was paused.

**Via the console:** Click **Approve** in the run detail panel.

**Via the API:**

```bash
curl -X POST https://overture.igrisinertial.com/v1/execution/runs/exec-01HXYZ/approve \
  -H "Authorization: Bearer YOUR_API_KEY"
# → {"status": "RUNNING", "approved": true}
```

The run resumes on the next heartbeat from its runtime instance — typically within a few seconds.

The approval timestamp and the identity of the approving API key are recorded in the receipt immediately on the approve call, before the run resumes.

---

## Rejecting a Run

Rejection terminates the run. It does not resume. The status transitions to REJECTED and a receipt is issued recording the rejection.

**Via the console:** Click **Reject** in the run detail panel and enter a reason in the prompt.

**Via the API:**

```bash
curl -X POST https://overture.igrisinertial.com/v1/execution/runs/exec-01HXYZ/reject \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"reason": "action_out_of_scope"}'
# → {"status": "REJECTED", "reason": "action_out_of_scope"}
```

The `reason` field is free text. Use it consistently — rejection reasons feed into policy improvement over time and appear in the audit log. Common reason strings: `action_out_of_scope`, `unexpected_target`, `policy_violation`, `manual_review_failed`, `test_rejection`.

The agent cannot retry a rejected run. Use replay if you want to re-run the same inputs after addressing the underlying issue.

## What Gets Recorded in the Receipt

Every approve or reject decision is appended to the run's signed execution receipt as an `approval_event`. The receipt is re-signed after the event is appended, making any subsequent modification detectable.

```json
{
  "execution_id": "exec-01HXYZ",
  "agent_id": "agent-abc",
  "status": "REJECTED",
  "approval_event": {
    "action": "reject",
    "approved_by": "[api-key-id]",
    "approved_at": "2026-03-31T10:19:07Z",
    "reason": "action_out_of_scope"
  },
  "signature": "sha256:c4a1..."
}
```

For an approved run that subsequently completes:

```json
{
  "execution_id": "exec-01HABC",
  "agent_id": "agent-abc",
  "status": "COMPLETED",
  "approval_event": {
    "action": "approve",
    "approved_by": "[api-key-id]",
    "approved_at": "2026-03-31T10:22:14Z",
    "reason": null
  },
  "signature": "sha256:d7f3..."
}
```

| Field | Meaning |
|---|---|
| `action` | `approve` or `reject` |
| `approved_by` | The API key prefix of the approver (or the console user's account ID if approved via the console) |
| `approved_at` | ISO 8601 timestamp of the decision |
| `reason` | Free-text reason (present for rejections; null for approvals) |

## Replaying a Rejected Run

Replay creates a new run with the same inputs as the original. It does not modify the original run's receipt — the rejection stands as a permanent record.

```bash
curl -X POST https://overture.igrisinertial.com/v1/execution/runs/exec-01HXYZ/replay \
  -H "Authorization: Bearer YOUR_API_KEY"
# → {"status": "replayed", "new_execution_id": "exec-01HABC"}
```

The new run starts fresh with a new `execution_id`. It will go through the same policy evaluation, including HITL triggers — so if the underlying conditions have not changed, it may be paused again.

Use replay after:
- Updating the agent's policy to adjust capability grants or review triggers
- Confirming that the intended action is now within scope
- Investigating and resolving the reason for the original rejection

## Monitoring the Approval Queue

For production deployments, treat the HITL queue depth as an operational metric. Runs that sit in the queue for too long block the agent pipeline — the agent is not proceeding, and downstream processes may be waiting.

To track queue depth via the alerts API:

```bash
curl "https://overture.igrisinertial.com/v1/history/alerts?unacknowledged=true" \
  -H "Authorization: Bearer YOUR_API_KEY"
```

Alerts are raised when a run enters the HITL queue. Acknowledge an alert when you begin reviewing it, resolve it when the decision is made.

## Best Practices

**Set a response SLA.** Decide how long a run can sit in the approval queue before it must be acted on or escalated. A 15-minute SLA is a common starting point for operational systems. Stale PAUSED runs block dependent pipelines.

**Record a reason for every rejection.** Even if the rejection is routine, consistent reason strings make the audit log useful over time and help identify patterns in what the agent is attempting.

**Use shadow mode to validate triggers before production.** If you are introducing new HITL review triggers, test them with a shadow agent first. Shadow agents produce receipts (including would-be pause events) without pausing production traffic.

**Do not replay blindly.** Replay is most useful after you have changed something — a policy update, a capability grant, an agent configuration change. Replaying without addressing the root cause of the rejection will likely result in another pause or rejection.

**Audit approval events regularly.** The approval event in each receipt shows who approved what and when. Review this data during periodic audits to verify that approval decisions are consistent with your operational policy.
