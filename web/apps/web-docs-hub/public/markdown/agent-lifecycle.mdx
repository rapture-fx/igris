# Agent Lifecycle

Every agent running on the execution engine has a tracked lifecycle. State transitions are deterministic, signed, and queryable — giving you a full audit trail of every agent's history from initialization to termination.

---

## States

| State | Meaning |
|---|---|
| `INIT` | Agent registered, not yet started |
| `RUNNING` | Actively processing a request |
| `IDLE` | Waiting for the next request |
| `DEGRADED` | Repeated failures; execution continues with reduced confidence |
| `SAFE_IDLE` | Paused pending human review or approval |
| `RECOVERING` | Restarting after a violation or crash |
| `TERMINATED` | Permanently stopped; no further requests accepted |

---

## State Transitions

```
INIT → RUNNING
RUNNING → IDLE         (request completed normally)
RUNNING → DEGRADED     (error threshold exceeded)
RUNNING → SAFE_IDLE    (human approval required)
IDLE → RUNNING         (new request received)
DEGRADED → RECOVERING  (recovery triggered)
RECOVERING → IDLE      (recovery succeeded)
RECOVERING → TERMINATED (recovery failed)
SAFE_IDLE → RUNNING    (approval granted)
SAFE_IDLE → TERMINATED (approval denied)
* → TERMINATED         (explicit shutdown or fatal error)
```

---

## Querying Agent State

```bash
# Get the state for one local runtime agent
curl http://localhost:8080/v1/runtime/agent/agent-abc/state \
  -H "Authorization: Bearer YOUR_API_KEY"
```

Response:

```json
{
  "agent_id": "agent-abc",
  "state": "IDLE",
  "created_at": "2026-03-01T10:00:00Z",
  "last_transition": "2026-03-01T12:05:00Z",
  "total_requests": 47,
  "violations": 0
}
```

The current local runtime API exposes state for a single known agent ID. Fleet-wide runtime lists are available through the swarm and fleet coordination APIs rather than the agent lifecycle endpoint.

---

## Lifecycle Records

Each state transition is recorded as a signed lifecycle event:

```json
{
  "agent_id": "agent-abc",
  "from_state": "RUNNING",
  "to_state": "IDLE",
  "trigger": "request_completed",
  "timestamp": "2026-03-01T12:05:00Z",
  "signature": "sha256:d4e1..."
}
```

Lifecycle records are hash-chained and included in the audit log alongside execution receipts.

## Canceling In-Flight Work

```bash
curl -X POST http://localhost:8080/v1/runtime/task/task-abc/cancel \
  -H "Authorization: Bearer YOUR_API_KEY"
```

Cancellation is task-scoped in the current runtime API. A canceled task is recorded in the runtime task history and its receipt/WAL evidence remains available for reconciliation.

---

## Safe Idle (Human-in-the-Loop)

When an agent enters `SAFE_IDLE`, it pauses execution and waits for an explicit approval signal. This is triggered by:
- Execution cost exceeding a per-agent budget
- A capability violation that requires human review
- Policy rules requiring approval for high-stakes actions

The waiting period, approval identity, and decision are all recorded in the receipt.

---

## Recovery

The `RECOVERING` state is entered when a runtime goes dark mid-execution. The coordination layer detects stale heartbeats (> 90 seconds) and reassigns all in-flight tasks from that runtime to a healthy one.

Recovery is exact, not approximate. When durable task execution is in use, the coordination layer forwards a `ResumeToken` containing the last committed step index and a rolling checkpoint digest to the new runtime. The new runtime verifies the digest against its local WAL before skipping any steps. Execution resumes from exactly where it stopped.

For agents and workflows without a WAL session, recovery restarts the task from the beginning. Enabling durable task execution on long-running workflows is recommended whenever precise resume matters.

The recovery loop runs every 15 seconds. There is no manual trigger — recovery is fully automatic.
