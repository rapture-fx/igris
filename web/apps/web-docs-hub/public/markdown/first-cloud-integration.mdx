# First Hosted Integration

Igris runs **registered actions**. Instead of letting an agent call provider and tool APIs directly, you register the action once — what it does, where it runs, and what policy governs it — and the agent calls that action through one stable endpoint. Igris handles policy, tenant-scoped idempotency, routing, recovery, and proof.

The first integration is four steps:

1. Create a tenant API key
2. Register an action
3. Run the action with an idempotency key
4. Inspect the run

---

## 1. Create A Tenant API Key

Create one tenant API key for the environment that will call the hosted API. Treat it like any other production secret and keep it in your standard secret store.

- [Trial & Billing →](/docs/trial-billing)
- [API Authentication →](/docs/api-reference/authentication)

## 2. Register An Action

An action definition is the contract for what an agent may ask Igris to run. This example registers a webhook-backed action that sends an invoice through your billing system:

```bash
curl -X POST https://overture.igrisinertial.com/v1/actions \
  -H "Authorization: Bearer $IGRIS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "send_invoice",
    "display_name": "Send invoice",
    "description": "Send an invoice to a customer through the billing webhook.",
    "target_type": "webhook",
    "target_url": "https://billing.example.com/hooks/igris",
    "policy_preset": "Safe automation"
  }'
```

A few things worth knowing before you pick values:

- `target_type` decides where the action runs: `webhook` and `hosted_api` call an HTTP target, `local_runtime` runs on a runtime you install in your own environment, and `mock_demo` is a safe demo target that never calls an external API.
- `policy_preset` governs every run. `Human-gated` pauses each run for approval; `Read-only` and `Non-replayable` constrain what recovery may do.
- The full field list is in the [Actions API reference →](/docs/api-reference/actions/post-v1-actions).

## 3. Run The Action

Agents and services run the action by name. Send an `idempotency_key` whenever a retry could double-run real work — retries with the same key inside your tenant return the original run instead of running the action again:

```bash
curl -X POST https://overture.igrisinertial.com/v1/actions/send_invoice/run \
  -H "Authorization: Bearer $IGRIS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "input": { "customer_id": "cus_8821", "amount": 4200 },
    "idempotency_key": "invoice-8821-2026-06"
  }'
```

The response is a durable run acknowledgement:

```json
{
  "run_id": "018f4a2b-3c1e-7a2d-9b8f-4d5e6f7a8b9c",
  "status": "dispatched",
  "proof_status": "pending",
  "action_name": "send_invoice"
}
```

Two responses are expected behavior, not errors:

- `409 approval_required` — the action is human-gated; the run is paused until a reviewer approves it.
- `503 runtime_unavailable` — a `local_runtime` action has no connected runtime; Igris refuses up front instead of queueing work that cannot execute.

This is the same path everywhere: tenant identity always comes from your credential (never from the request body), and only registered actions can run — the endpoint does not accept raw execution definitions.

## 4. Inspect The Run

Every run is durable and inspectable after the fact:

```bash
curl https://overture.igrisinertial.com/v1/actions/runs/018f4a2b-3c1e-7a2d-9b8f-4d5e6f7a8b9c \
  -H "Authorization: Bearer $IGRIS_API_KEY"
```

You get lifecycle status, proof status, and a redacted input summary. Run inputs are never echoed back raw — inspection returns digests and safe summaries, so the evidence stays reviewable without exposing payloads.

When the run completes, the proof and receipt records show what happened as safe execution metadata. Start with [Execution Receipts →](/docs/execution-receipts) when you need audit evidence.

## Where To Go Next

- **Give the same action to an MCP agent.** The MCP `call_action` tool uses exactly this registered-action path — same policy, same idempotency, same evidence. See [MCP →](/docs/mcp).
- **Run actions in your own environment.** For private files, internal APIs, or local databases, register a `local_runtime` action and install a runtime. Igris pushes work to your registered runtime endpoint, so that endpoint must be reachable by Overture. See [Deploy Local Runtime →](/docs/deploy-local-runtime).
- **Use the SDK.** The JavaScript/TypeScript SDK wraps this flow in `client.runAction(...)`. See [SDKs →](/docs/sdk).

## Common Mistakes

- Retrying a run without an `idempotency_key` and double-running a side effect that mattered
- Treating `409 approval_required` as a failure instead of the expected human-gated pause
- Registering a `webhook` or `hosted_api` action without a `target_url`, then wondering why runs return `target_not_configured`
- Letting agents call provider APIs directly and losing the policy, recovery, and evidence trail that registered actions give you
