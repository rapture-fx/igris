# Policy

Policy in Igris is the mechanism for controlling what AI tasks are allowed to do.

In Request -> Execute -> Verify terms:

- **Request** carries intent and scope
- **Execute** applies policy checks and boundaries
- **Verify** exposes the resulting events and records for review

This page is about execution control, not about presenting policy as a broad platform claim detached from execution behavior.

---

## What Policy Controls

Policy helps determine:

- which tools or actions are allowed
- which boundaries apply to the run
- what should happen when the run exceeds those boundaries
- what review signals should be available afterward

That makes policy a live part of execution, not just static configuration.

## Tool And Permission Boundaries

Policy can express boundaries such as:

| Area | What it controls |
|---|---|
| Tool access | Which tools or external actions are allowed |
| Domain or target restrictions | Where HTTP or similar actions may reach |
| Resource limits | Duration, step, or token limits |
| Review expectations | Which outcomes should trigger operator follow-up |

When a run exceeds these boundaries, that result should appear in the execution record and follow-up surfaces.

## Execution-Time Effects

Policy matters during execution because it shapes what the task is allowed to do in practice.

Examples:

- rejecting disallowed actions
- constraining tool scope
- limiting resource use
- surfacing violations for later inspection

This is why policy belongs next to governance and verification in the docs.

## Policy And Records

Policy is most useful when its effect can be inspected afterward.

After a run, operators should be able to move into:

- execution events and history
- receipt-oriented records
- verification surfaces that show what was actually recorded

Use:

- [Governance →](/docs/governance)
- [History & Alerts →](/docs/history)
- [Verification →](/docs/verification)

## Routing Policy Should Stay Secondary Here

There are routing-related policy surfaces in the broader product, but this page should not lead with routing sophistication. The primary mental model is still controlling what execution is allowed to do.

If you need routing-specific depth, use the more specialized routing pages rather than turning policy into a routing-first introduction.

## Common Mistakes

- Treating policy as only a preflight configuration layer instead of an execution control
- Describing policy as a full generalized compliance platform without tying it to execution behavior
- Explaining policy in routing terms before explaining boundaries and permission checks
- Skipping the follow-up step of checking history, receipts, or verification surfaces after a policy-sensitive run
