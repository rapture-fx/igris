# Speculative Execution

Speculative execution runs a lightweight draft inference in parallel with the main inference. When the draft result meets a quality threshold, it is returned immediately — before the main inference completes. This reduces time-to-first-token by up to 60% for streaming requests, at no change to output quality for the workloads where it applies.

---

## How It Works

When speculative execution is enabled, each incoming inference request spawns two parallel paths:

1. **Draft path** — A faster, smaller model generates a candidate response. The draft is evaluated for quality as it streams.
2. **Main path** — The configured primary model processes the request normally.

If the draft meets the acceptance threshold before the main inference completes, the draft is returned immediately and the main inference is cancelled. If the draft does not meet the threshold — because the task is too complex or unpredictable for the draft model — the main inference result is returned instead.

The caller always receives one response. The distinction between draft and main is not exposed in the response payload. The execution receipt records which path was used.

---

## When It Helps

Speculative execution provides the most benefit in these scenarios:

**Streaming responses with latency requirements.** The time-to-first-token improvement is most noticeable in streaming use cases where users are waiting for a response to begin. Draft acceptance reduces the delay before the first token arrives.

**Repetitive or predictable completions.** Tasks like summarization, translation, structured data extraction, and templated generation tend to have high draft acceptance rates because the output space is constrained and the draft model handles them well.

**High-throughput batch workloads where p50 latency is a key metric.** At scale, improving the median case across many requests compounds into a significant reduction in overall processing time.

---

## When It Does Not Help

**Non-streaming requests.** For non-streaming calls, the latency benefit is smaller because the caller waits for the full response regardless. Speculative execution still applies, but the improvement to perceived latency is minimal.

**Highly creative or open-ended tasks.** Tasks like long-form creative writing, complex multi-step reasoning, or novel problem-solving tend to have low draft acceptance rates — the draft model produces a candidate that does not meet the quality threshold, so the main inference result is used anyway. In these cases, speculative execution adds overhead without benefit.

**Workloads where correctness is paramount and draft quality is consistently low.** If your analytics show a low `draft_acceptance_rate` for a particular agent or task type, speculative execution is likely not beneficial for that workload. Disable it per-tenant or evaluate per-agent after reviewing the analytics.

---

## Tier Availability

Speculative execution is available on all tiers. On Seed, it runs with a single draft model. On Horizon and Infinite, you can configure multiple draft models and set custom acceptance thresholds.

## Enabling Speculative Execution

### Enable for your tenant

```bash
curl -X POST https://overture.igrisinertial.com/v1/routing/speculative \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"enabled": true}'
# → {"enabled": true, "updated_at": "2026-03-31T09:00:00Z"}
```

To disable:

```bash
curl -X POST https://overture.igrisinertial.com/v1/routing/speculative \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"enabled": false}'
```

Changes take effect on the next request. There is no restart required.

### Check live status

```bash
curl https://overture.igrisinertial.com/v1/routing/speculative/status \
  -H "Authorization: Bearer YOUR_API_KEY"
```

Response:

```json
{
  "enabled": true,
  "currently_active": true,
  "draft_model": "phi-3-mini",
  "requests_since_enabled": 4821
}
```

`currently_active` indicates whether speculative execution is actively being applied to incoming requests, as distinct from being configured. If `enabled` is true but `currently_active` is false, check whether the tenant has a valid provider key configured — speculative execution requires at least one cloud provider to be available.

## Reading Analytics

```bash
curl https://overture.igrisinertial.com/v1/routing/speculative/analytics \
  -H "Authorization: Bearer YOUR_API_KEY"
```

Response:

```json
{
  "period": "last_24h",
  "total_requests": 4821,
  "draft_accepted": 3289,
  "draft_acceptance_rate": 0.682,
  "avg_latency_reduction_ms": 412,
  "main_inference_used": 1532,
  "savings_estimate_ms_total": 1354668
}
```

**Field reference:**

| Field | Meaning |
|---|---|
| `draft_acceptance_rate` | Fraction of requests where the draft was accepted and returned (0–1). Higher is better. |
| `avg_latency_reduction_ms` | Average reduction in time-to-first-token on requests where the draft was accepted. |
| `main_inference_used` | Number of requests where the draft was rejected and the main inference result was returned. |

**Interpreting acceptance rate:**

A `draft_acceptance_rate` above 0.60 indicates speculative execution is delivering meaningful value for your workload. Between 0.40 and 0.60, the benefit is moderate — weigh the latency improvement against any added complexity. Below 0.40, speculative execution is accepting fewer than 4 in 10 drafts, and the overhead of running two parallel paths may not be worth it for most of your requests.

If acceptance rate is consistently low, consider whether the workload is a good fit. Run the simulation endpoint on a representative sample request to get a pre-enablement estimate.

## Simulating Before Enabling

The simulate endpoint runs a dry-run of speculative execution on a sample request and reports whether the draft would have been accepted and what the estimated latency reduction would be. Use this to evaluate benefit before enabling for production traffic.

```bash
curl -X POST https://overture.igrisinertial.com/v1/routing/speculative/simulate \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "messages": [
      {"role": "user", "content": "Summarize the following meeting notes in three bullet points: ..."}
    ],
    "model": "gpt-4o"
  }'
```

Response:

```json
{
  "draft_would_accept": true,
  "estimated_latency_reduction_ms": 380,
  "draft_quality_score": 0.87,
  "main_inference_time_ms": 1120,
  "draft_inference_time_ms": 740
}
```

If `draft_would_accept` is consistently false across several representative samples, the workload is unlikely to benefit from speculative execution at scale.

## Interaction with Other Features

**Council mode:** Council mode is applied to the main inference path — speculative execution and council mode are independent. When a draft is accepted, council mode does not run on that request (the draft is a single-model result). When the draft is rejected, the full council evaluation runs on the main inference as configured.

**Shadow mode:** Shadow mode agents run their execution against the full main inference, not the draft path. Shadow comparisons reflect what the primary model would produce without speculative acceleration.

**Execution receipts:** Receipts always record the result that was actually returned to the caller. If the draft was accepted, the receipt reflects the draft result. If the main inference was used, the receipt reflects the main inference result. The `speculative_draft_used` field in the receipt indicates which path was taken.

```json
{
  "execution_id": "exec-01HXYZ",
  "speculative_draft_used": true,
  "wall_time_ms": 743
}
```

**Routing Advisor:** The routing advisor tracks speculative acceptance rates as part of its routing telemetry. If acceptance rate falls below a threshold, the advisor may propose disabling speculative execution for the affected workload.
