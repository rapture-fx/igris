# Deploy Local Runtime

Use this workflow when Igris should execute closer to where the work happens.

Local runtime is not a separate product identity. It is an execution surface for workloads that benefit from locality, device-level boundaries, or reduced dependence on a hosted path.

Choose this path when you need:

- execution near the machine or device doing the work
- local policy enforcement or bounded task handling
- offline or low-connectivity operation
- runtime-local behavior tree or tool execution

If those properties are not central to the workload, start with the hosted integration first.

---

## 1. Download The Runtime Archive

Use the runtime distribution endpoints for your platform and treat download as provisioning, not application traffic.

```bash
export IGRIS_PLATFORM="linux-amd64"

curl -fL "https://overture.igrisinertial.com/v1/runtime/install?platform=${IGRIS_PLATFORM}" \
  -o /tmp/igris-runtime.tar.gz

curl -fL "https://overture.igrisinertial.com/v1/runtime/checksum?platform=${IGRIS_PLATFORM}"
```

Verify the archive checksum before installation.

## 2. Install The Binary

```bash
tar -xzf /tmp/igris-runtime.tar.gz -C /tmp
mkdir -p "$HOME/.local/bin"
mv /tmp/igris-runtime "$HOME/.local/bin/igris-runtime"
chmod +x "$HOME/.local/bin/igris-runtime"
export PATH="$HOME/.local/bin:$PATH"
```

## 3. Configure Auth And Local Execution Behavior

Create `~/.config/igris/config.json5`:

```json5
{
  server: {
    host: "0.0.0.0",
    port: 8080
  },
  auth: {
    enabled: true,
    api_key: "YOUR_IGRIS_API_KEY"
  },
  local_fallback: {
    enabled: true,
    model_path: "/models/phi-3-mini-4k-instruct-q4.gguf",
    context_size: 4096,
    threads: 4,
    n_gpu_layers: 0
  }
}
```

This configuration expresses how the runtime should execute work locally. Treat local GGUF fallback carefully in public claims: the code path exists, but reproducible proof should be checked against [Proof Status](/docs/proof-status) before you present it as a guaranteed behavior.

## 4. Start And Verify The Runtime

```bash
igris-runtime serve
curl http://localhost:8080/v1/health
```

Once the runtime is healthy, use the runtime base URL for local requests:

```text
http://localhost:8080/v1
```

## 5. Send A Local Request

```typescript
import OpenAI from 'openai';

const client = new OpenAI({
  baseURL: 'http://localhost:8080/v1',
  apiKey: process.env.IGRIS_API_KEY,
});

const response = await client.chat.completions.create({
  model: 'phi3',
  messages: [{ role: 'user', content: 'Hello from local runtime' }],
});
```

This is still the same execution model:

- **Request** through an Igris API surface
- **Execute** on the local runtime path
- **Verify** with the records and receipts returned by the configured workflow

## Two Ways Work Reaches the Runtime

There are two distinct paths, and they have different networking requirements.

**1. Direct local requests.** When your own client calls the runtime's base URL
(`http://localhost:8080/v1`), as in the step above, the runtime only needs to be
reachable by *that client*. A localhost or LAN address is fine.

**2. Cloud-dispatched work.** When an action targets a local runtime, the hosted
control plane delivers the work by **sending it to the runtime's registered
endpoint** — the cloud reaches out to your runtime, not the other way around. For
this path the registered endpoint must be an `http(s)` URL that **Igris can reach**.

A `localhost` or private LAN address (for example `http://127.0.0.1:8080` or
`http://10.0.0.12:8080`) is **not** reachable from the hosted control plane, so a
runtime registered with such an endpoint cannot receive cloud-dispatched actions.
For cloud dispatch, expose the runtime on a publicly reachable URL — a stable public
host, a reverse proxy, or a tunnel — and register that URL.

If you are only making direct local requests, you do not need a publicly reachable
endpoint at all. Choose the path that matches your workload before exposing anything.

## Register the Runtime for Fleet and Dispatch

To appear in Fleet and to receive cloud-dispatched actions, the runtime registers
itself with the control plane using your API key. Registration includes the endpoint
described above, and the control plane rejects an endpoint it cannot treat as a
routable `http(s)` URL. See
[POST /api/v1/runtime/register](/docs/api-reference/runtime-distribution-fleet-coordination/post-api-v1-runtime-register)
for the field contract.

## Where the Binary Comes From

The download and install endpoints serve the official runtime build. In hosted
production the authenticated download and the public installer resolve to the
published runtime release artifacts (GitHub Releases is the source of truth for those
binaries). Always verify the checksum before installing, regardless of source.

## What To Say Carefully

- Local execution is real and supported.
- Local runtime is an execution surface, not a different product.
- Local GGUF fallback should be treated as source-confirmed or in development unless you have a reproducible proof path for the exact scenario you are describing.

## Common Mistakes

- Pointing a local-only client at the hosted base URL
- Treating runtime download or install as hot-path application traffic
- Assuming local execution automatically proves local fallback, checkpoint recovery, or fleet behavior
- Mixing hosted and local URLs without being explicit about which surface owns the request
