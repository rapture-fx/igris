# Hybrid Execution Architecture

Igris Inertial splits inference work across two planes: a decision plane (Overture) and an execution plane (Runtime). Each plane has a distinct responsibility. Requests flow from the SDK through Overture, into the Runtime, and back — with cryptographic verification at each boundary.

This page covers the execution architecture. For trust verification, audit trails, and observed vs reported verification, see [Hybrid Execution (trust verification)](/docs/hybrid-execution).

---

## Two Planes, One Request

### Overture — Decision Plane

Overture is the control plane. It never performs inference directly. Its responsibilities are:

- Authenticating SDK callers and enforcing rate limits and budget checks
- Selecting the provider and model using the configured routing policy (Thompson Sampling, speculative, council, cost-aware)
- Signing the routing decision before forwarding to a Runtime instance
- Selecting a healthy Runtime from the registry
- Verifying the Runtime's signed execution envelope
- Assembling and returning the final response to the SDK

Overture holds no model weights and performs no inference. Its output for each request is a routing decision — which Runtime to use, which provider to call, and under what constraints.

### Runtime — Execution Plane

The Runtime is the execution plane. It receives signed routing decisions from Overture and is responsible for:

- Verifying the incoming routing decision (Bearer auth and, if configured, Ed25519 signature)
- Executing inference under configured resource bounds (CPU quota, memory limit, tick deadline)
- Enforcing containment — requests that exceed bounds are killed unconditionally
- Returning a signed execution envelope with the response and observed metrics
- Recording bound violations in a signed JSONL log

The Runtime does not communicate directly with SDKs. All requests arrive from Overture.

---

## Request Lifecycle

1. SDK calls `POST /v1/infer`
2. Overture authenticates the caller, checks rate limits and budget
3. Overture selects a healthy Runtime from the registry using health-based selection
4. Overture signs the request and forwards it to the selected Runtime with containment bounds
5. Runtime verifies the request, executes under containment, returns a signed result
6. Overture verifies the execution envelope signature, records the audit entry, and returns the response to the SDK

---

## Runtime Registry

When multiple Runtime instances are registered via `POST /api/v1/runtime/register`, Overture manages them through a health-based registry:

- Polls each instance's `/v1/health` endpoint every 30 seconds
- Maintains health state and instance metadata in the database
- Routes requests to healthy instances, preferring edge instances over cloud instances when both are available
- Applies a circuit breaker with a threshold of 3 consecutive failures; instances that trip the breaker are temporarily bypassed

When all registered instances have open circuit breakers, Overture falls back to direct provider routing. This is the only condition under which Runtime is bypassed without a hard failure.

---

## Failure Modes

| Failure | Behavior |
|---|---|
| All Runtime instances unhealthy | Falls back to direct provider routing |
| Circuit breaker open for one instance | Skip that instance, try the next healthy one |
| Circuit breaker open for all instances | Falls back to direct provider routing |
| Runtime returns 401 or 403 | Hard fail — 502 returned to SDK |
| Runtime execution envelope signature invalid | Hard fail — 502 returned to SDK |
| Runtime timeout or network error | Falls back to direct provider routing |

Security verification failures (401, 403, invalid envelope signature) are always hard-rejected. Availability failures (timeout, network error, all instances unhealthy) fall back to direct provider routing.

---

## Containment Bounds

Overture attaches containment limits to every request forwarded to a Runtime instance via the `X-Igris-Bounds` header:

```json
{
  "cpu_percent": 40,
  "memory_mb": 512,
  "max_tick_ms": 5000
}
```

These bounds are enforced by the Runtime at the OS level. A request that exceeds `max_tick_ms` is killed unconditionally — there is no grace period. Bound violations are recorded in a signed JSONL log on the Runtime host.

Containment bounds apply uniformly to all execution modes: standard completions, streaming, speculative execution, and council mode.
