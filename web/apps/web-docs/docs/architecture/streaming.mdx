# Streaming & Enforcement

When a Runtime instance is configured and healthy, all request types route through it — including streaming requests, speculative execution, and council mode. There is no streaming-only bypass. Containment bounds and the cryptographic trust chain apply uniformly regardless of execution mode.

---

## Execution Modes

### Standard Completions

Standard (non-streaming) inference requests route through the Runtime's `/v1/runtime/task/submit` endpoint as `single_inference` tasks. The Runtime executes under containment bounds and returns a signed execution envelope with the complete response.

### Streaming Completions

When `stream: true` is set and a Runtime instance is available:

1. Overture forwards the request to the Runtime at the same `/v1/runtime/task/submit` endpoint
2. The Runtime executes under containment bounds
3. The Runtime returns a complete JSON response (not a chunked stream)
4. Overture reconstructs the response as an SSE stream and returns it to the SDK

The SSE stream that the SDK receives is assembled by Overture from the Runtime's complete JSON response. There is no chunked HTTP connection between Overture and the Runtime. From the SDK's perspective, the response looks identical to a direct streaming response.

Streaming requests observe the same `max_tick_ms` containment deadline as non-streaming requests. If execution exceeds the deadline, the Runtime kills the request unconditionally.

### Speculative Execution

Speculative execution (racing 2–3 providers in parallel) routes through the Runtime when configured. The Runtime executes the winning provider's request under containment bounds. The trust chain applies in full.

### Council Mode

Council mode routes through the Runtime when configured. Council mode disables streaming: if `council_mode: true` and `stream: true` are both present in the same request, streaming is disabled before the request is forwarded to the Runtime.

---

## Containment Bounds for Streaming

Containment bounds apply to all execution paths, including streaming. Overture includes them in the signed runtime task body:

```
{
  "containment": {"cpu_percent":40,"memory_mb":512,"max_tick_ms":5000}
}
```

For requests where the expected generation time is longer than the default deadline, set `max_tick_ms` to an appropriate value when registering the Runtime or when constructing the request. Requests that exceed the deadline are killed without a grace period, and the SDK receives an error — not a partial stream.

---

## Failure Semantics

| Condition | Behavior |
|---|---|
| Runtime security verification fails (any mode) | 502 Bad Gateway, no fallback |
| Runtime timeout during streaming | Falls back to direct provider streaming |
| No healthy Runtime instance | Direct provider routing; SSE delivered directly from provider |

Security verification failures are hard-rejected regardless of execution mode. Availability failures fall back to direct provider routing, including for streaming requests.

---

## SDK Example

The following example shows a streaming request through a Runtime-backed Overture instance with explicit containment bounds. The SDK usage is identical to standard OpenAI-compatible streaming — the Runtime is transparent from the SDK's perspective.

```python
from igris import Overture, Bounds

client = Overture(api_key="...")

# Streaming through Runtime — containment bounds apply
for chunk in client.chat.completions.stream(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Explain relativity"}],
    bounds=Bounds(cpu_percent=50, max_tick_ms=10000),
):
    print(chunk.delta, end="", flush=True)
```

The `bounds` parameter is forwarded inside the signed runtime task payload. If the request exceeds `max_tick_ms` (10 seconds in this example), the Runtime kills it and Overture returns an error to the SDK.
