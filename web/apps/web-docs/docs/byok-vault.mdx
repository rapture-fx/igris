# Provider Key Vault (BYOK)

Igris Overture never uses shared provider credentials. Every tenant provides their own API keys, which are encrypted and stored in the vault. Your keys are yours — isolated, rotatable, and never visible to other tenants.

---

## How It Works

When you make a request through Overture, the routing engine selects a provider from your configured pool. It retrieves your key for that provider from the vault, makes the request on your behalf, and returns the response. Your key is never logged, never returned in API responses, and never shared.

```
Your App → Overture API → Vault (decrypts your key) → Provider API
```

---

## Adding Keys

Store a provider API key:

```bash
curl -X POST https://api.igrisinertial.com/v1/vault/keys \
  -H "Authorization: Bearer YOUR_IGRIS_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "openai",
    "key": "sk-..."
  }'
```

Supported providers: `openai`, `anthropic`, `google`, `mistral`, `cohere`, `deepseek`, `groq`.

---

## Listing Keys

List which providers you have keys configured for. Keys are never returned — only provider names and metadata:

```bash
curl https://api.igrisinertial.com/v1/vault/keys \
  -H "Authorization: Bearer YOUR_IGRIS_KEY"
```

```json
[
  {
    "provider": "openai",
    "added_at": "2026-01-15T10:30:00Z",
    "last_used": "2026-03-01T14:22:00Z",
    "status": "active"
  },
  {
    "provider": "anthropic",
    "added_at": "2026-01-20T09:00:00Z",
    "last_used": "2026-03-01T14:20:00Z",
    "status": "active"
  }
]
```

## Validating a Key

Test that a stored key is valid and the provider is reachable before relying on it for routing:

```bash
curl -X POST https://api.igrisinertial.com/v1/vault/keys/openai/validate \
  -H "Authorization: Bearer YOUR_IGRIS_KEY"
```

```json
{
  "provider": "openai",
  "valid": true,
  "latency_ms": 234,
  "message": "Key is valid and provider is reachable"
}
```

Use this after initial key setup and after rotation.

---

## Rotating Keys

Rotate a provider key without downtime. The old key remains active until you confirm the new one:

```bash
curl -X POST https://api.igrisinertial.com/v1/vault/keys/openai/rotate \
  -H "Authorization: Bearer YOUR_IGRIS_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "new_key": "sk-new-key..."
  }'
```

The rotation is atomic — in-flight requests complete with the old key, new requests use the new key immediately after the rotation API call returns.

---

## Removing Keys

Remove a provider key. Overture will stop routing requests to that provider:

```bash
curl -X DELETE https://api.igrisinertial.com/v1/vault/keys/openai \
  -H "Authorization: Bearer YOUR_IGRIS_KEY"
```

If this was your only configured provider, subsequent requests will fail. Ensure you have at least one provider key configured at all times.

---

## Security Model

**Encryption at rest.** All keys are encrypted before storage using AES-256-GCM with a per-tenant key.

**No plaintext access.** The vault API never returns a stored key in plaintext. The `list` endpoint returns only provider names and metadata.

**Tenant isolation.** Each tenant's vault is fully isolated. There is no shared key pool.

**Audit logging.** Key additions, removals, and rotations are recorded in the audit log with timestamps. Key usage (which provider was called when) is tracked per-request.

---

## Per-Provider Key Usage

Once you have multiple provider keys, Overture's routing engine selects which to use per-request based on your routing policy and current provider health. You don't specify a provider per-request — the routing engine decides.

To see which provider handled a specific request:

```python
response = client.chat.completions.create(...)
print(response.metadata.provider)  # "anthropic"
```
