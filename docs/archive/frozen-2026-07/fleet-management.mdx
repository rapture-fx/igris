# Fleet Management

Use fleet management when you need visibility into the execution environments that participate in Igris workflows.

This page is about operating registered runtime environments. The reliable, practical use cases today are:

- registering execution environments
- monitoring whether they remain visible and healthy enough to participate
- inspecting runtime coordination surfaces
- using queued command and rollout features carefully

---

## 1. Register Execution Environments

The stock runtime attempts registration automatically when both `IGRIS_LICENSE_KEY` and `IGRIS_API_KEY` are present at startup.

If you are integrating a custom launcher, use the runtime registration contract:

```bash
curl -X POST https://overture.igrisinertial.com/api/v1/runtime/register \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "machine_id": "edge-gateway-01",
    "hostname": "edge-gateway-01",
    "platform": "linux-amd64",
    "runtime_version": "1.6.0",
    "endpoint": "http://192.168.1.100:8080",
    "public_key_ed25519": "YOUR_RUNTIME_PUBLIC_KEY",
    "timestamp_unix_ms": 1775283660000,
    "signature": "YOUR_RUNTIME_SIGNATURE"
  }'
```

Registration is the first operator check: if the environment cannot register, it should not be treated as a participating execution surface yet.

## 2. Track Heartbeats And Coordination Surfaces

The main runtime coordination routes are:

- `POST /api/v1/runtime/heartbeat`
- `DELETE /api/v1/runtime/deregister`
- `GET /api/v1/runtime/commands`

These are runtime-to-hosted coordination surfaces. They are useful for operator workflows and automation, not as general application endpoints.

## 3. Inspect Registered Environments

Use the runtime governance summary when you want inventory and visibility:

```bash
curl https://overture.igrisinertial.com/v1/execution/governance/runtimes \
  -H "Authorization: Bearer YOUR_API_KEY"
```

Agents can read the same inventory through the MCP `list_runtimes` tool, which also reports whether each runtime is currently routable.

Use this surface to answer:

- which environments are registered
- which ones are still sending heartbeats
- which environments are actually visible to the control plane

That is the operator-safe meaning of fleet management in these docs.

## 4. Treat Config Push Carefully

Configuration push exists as an operator surface:

```bash
curl -X POST https://overture.igrisinertial.com/api/v1/runtime/config/push \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "selector": {"tags": ["site-a"]},
    "config": {
      "local_fallback": {
        "enabled": true,
        "model_path": "/models/phi-3-mini-q4.gguf"
      }
    }
  }'
```

Be precise about status:

- config push is experimental and disabled by default — it requires an explicit experimental feature flag on the deployment
- command queuing is real once the surface is enabled
- full end-to-end config rollout should still be treated according to [Proof Status](/docs/proof-status) unless you have a reproducible proof for your environment

## 5. Treat OTA-Style Updates Carefully

The update surface exists:

```bash
curl -X POST https://overture.igrisinertial.com/api/v1/runtime/update \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "version": "runtime-v1.6.0",
    "strategy": "rolling",
    "max_unavailable": 1
  }'
```

Use careful language here as well:

- the update route is experimental and disabled by default behind the same explicit feature flag
- staged update intent is part of the surface once enabled
- broader OTA behavior and multi-runtime failover claims should follow [Proof Status](/docs/proof-status)

## What Fleet Management Means In Practice

For most operators, fleet management currently means:

- register the right environments
- keep heartbeat visibility healthy
- inspect runtime presence before routing work toward those environments
- roll changes gradually and verify behavior after each stage

## Common Mistakes

- Treating registration surfaces like proof of fully automated fleet behavior
- Assuming queued command routes imply proven OTA or config execution in every environment
- Promoting multi-runtime failover as proven without a corresponding proof artifact
- Expanding the environment set before verifying that the first slice is healthy and inspectable
